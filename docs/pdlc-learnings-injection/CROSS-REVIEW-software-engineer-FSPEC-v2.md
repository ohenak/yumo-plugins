| F-01 | High | Cross-Feature | **BR-14's second malformed clause contradicts the precedent it cites, and AT-32 pins the divergence.** BR-14 defines malformed as "`learningsInjection` present and not an object, **or** present with a value of the wrong type for a declared key", and grounds both halves in "the reading the repository's sibling config readers already ship … `parseAdvisoryConfig` … and `parseMergeConfig` carries the same meaning". Only the first half is that reading. At HEAD, a wrong-typed value for a declared key is *not* malformed in either sibling: `parseAdvisoryConfig`'s `boolField`/`positiveInt`/`positiveNumber` push the key onto `invalidKeys` and substitute the declared default (`pdlc/workflows/orchestrate-dev.js:1989-2008`), returning `sectionMalformed: false` (`:2028`), and the run continues **enabled** with a non-fatal notice — `Advisory config: using defaults for {keys}` (`:13683-13684`). `sectionMalformed: true` is reached from exactly one place, the section-present-but-not-an-object guard (`:1981`; `parseMergeConfig` identically at `:123`). BR-14 instead routes a wrong-typed value into the baseline-identical row: an operator who writes `maxDocuments: "5"` gets the whole feature silently off for that run, where every other section of the same config file would have used 5 and carried on. That is a new cross-cutting config semantics for one feature, and it is the divergence-from-shipped-precedent case (DC-08). Either delete the clause and give wrong-typed declared keys the shipped treatment — per-key default, run stays enabled, catalogued notice naming the keys — or keep it and state the divergence as a deliberate decision with its reason, rather than as the siblings' meaning. Whichever way it lands, AT-32's second fixture and E-23 move with it. | BR-14, E-23, AT-32, Step 0.3 |
