## Findings

| F-01 | High | Cross-Feature | **The `_git` never-throws seam contract is false on the runtime channel, and the design's error strategy is built on it.** DEC-LI-02's Constraints row states "`_git(argv)` returns `{ok, stdout, stderr}` and never throws on either channel", and DEC-LI-04's Constraints row converts that into a design instruction: "the seam contract that `_git` never throws on either channel, so the shell's failure handling is a check of `ok`, not a `catch`". Read at HEAD, `rtGit` (`pdlc/workflows/runtime-adapter.js:1003`) awaits `RT.agent(...)` with **no** `try` — unlike every sibling transport wrapper in the same file (`rtReadChunk`, `rtReadProbe`, `rtHashFile`, `rtCliQuery` all wrap the `await RT.agent` in `try`). A rejected host `agent()` call therefore rejects `rtGit`, so `_git` **can** throw on the Claude Code channel. If IMPL follows the entry literally, that rejection propagates out of `gatherLearningsCorpus` and out of `dispatchAndVerify`, halting an authoring dispatch — the exact outcome REQ C-7/G-4 and FSPEC BR-12 ("no step raises to its caller") forbid. This is a testability finding as much as a correctness one: **every** test double for `_git` in this design returns `{ok: false}`, so no suite as specified can ever exercise a rejecting `_git`, and the fail-open claim would ship green and untested. Fix: correct both Constraints rows to state that `_git` never throws on the **Node** channel and may reject on the runtime channel; state that the IO shell's `try` covers both seams, not `_readFile` alone; and hand PROPERTIES/PLAN an explicit obligation for a `_git` double that **rejects** (not one that returns `{ok:false}`), asserting the dispatch still composes and records `RSN-UNLISTABLE`. | DEC-LI-02 §Constraints; DEC-LI-04 §Constraints |
| F-02 | High | Local | **DEC-LI-09 removes one vacuous-pass route and leaves its twin unguarded.** The entry rejects recomputing the merge-base because "a recomputed baseline can silently re-point at a commit that already contains feature code — the byte-identity test then compares the feature against itself and passes vacuously", and the chosen fix is to record the resolved sha in `MANIFEST.json`. But a *recorded* sha is only as good as the moment of capture: if capture is run after any production edit lands, the recorded sha is a commit that already contains feature code, and AC-6.2's byte-identity guard passes vacuously in exactly the way the entry names. The only defence offered is process — D-O-2, "capture ordered before the first production edit, as a binding gate" — and the entry does not say what makes that gate falsifiable, so the guard cannot notice its own vacuity. The guard test can cheaply assert the property directly against the recorded sha: `git merge-base --is-ancestor <recorded-sha> HEAD` **and** a positive-absence check that the subject module at `<recorded-sha>` contains none of this feature's exported symbols (e.g. `git show <sha>:pdlc/workflows/orchestrate-dev.js` has no `selectLearnings`). Fix: add that assertion to DEC-LI-09's Decision as part of what the guard checks, and make D-O-2 an obligation with that named oracle rather than an ordering promise. | DEC-LI-09 §Alternatives, §Reversibility; D-O-2 |
| F-03 | High | Local | **DEC-LI-06's no-cache decision names its own vacuous-green failure mode and then hands downstream no oracle against it.** The entry argues correctly that "a memo would let the determinism test pass **because the second call never happened**", and it classes its own reversibility as Hard precisely because a cache changes behaviour oracles depend on. Yet the obligations table carries an anti-reintroduction obligation for `present` (D-O-5, DEC-LI-07) and none for the cache — so the decision that is *hard* to reverse is the one with no test defending it, while the easy one has a named guard. Nothing in the suite as specified would red if IMPL added a run-scoped memo: a memoised run satisfies the determinism assertions more easily, not less. Fix: add a D-O row obliging a positive call-count oracle over a multi-dispatch run — `_git` enumeration calls **equal** the number of injecting dispatches, and `_readFile` calls for a selected document likewise — plus the E-32 behavioural case (a LEARNINGS document that lands between dispatch 1 and dispatch 2 appears in dispatch 2's selection, and an enumeration that succeeds at dispatch 1 and fails at dispatch 5 records `RSN-UNLISTABLE` at 5). The call-count conjunct matters on its own: the behavioural case alone can be satisfied by a memo keyed on something that happens to change. | DEC-LI-06 §Alternatives, §Reversibility; D-O table |
| F-04 | Medium | Local | **DEC-LI-03's leading re-evaluation trigger is unobservable, and the entry's own argument says why that is fatal.** The entry rejects the four-call-site alternative because "it drifts silently the moment a fifth authoring site appears: the new site simply does not inject, and no test fails, because the oracle (`AC-1.2`) is a set equality *against the run that happened*. A rule that cannot notice its own omission is not a rule." That reasoning applies unchanged to the chosen design's first re-evaluation trigger — "a fifth authoring code site appears that does **not** funnel through `dispatchAndVerify`" — which has no monitor at all: AC-1.2's oracle is computed from the same run record, so a non-funnelling site is invisible to it too. DEC-LI-04 already ships the right pattern for this class (a pinning test over a source-level literal). Fix: give DEC-LI-03 the analogous structural guard — a source-level test over `orchestrate-dev.js` asserting the set of authoring-classified dispatch producers (three `dispatchKind: "authoring"` object literals plus `runWrapped`'s positional `"authoring"`, verified at HEAD) is exactly the set that reaches `dispatchAndVerify`, with the expected set hand-transcribed — and name it in the trigger row so the trigger fires mechanically. | DEC-LI-03 §Alternatives, §Re-evaluation triggers |
| F-05 | Medium | Local | **D-O-3 omits the three parameterisable functions whose totality the design most depends on.** DEC-LI-02 declares `parseLearningsConfig`, `looksLikeLearningsDocument` and `parseHarvestDate` pure and "never throw"; DEC-LI-07 then makes `parseLearningsConfig`'s output the feature's **sole** gate, so a throw there takes the dispatch down. But D-O-3 obliges properties only over `orderCorpus`, `selectLearnings` and `extractInjectableMaterial`. A config parser, a document classifier and a date parser are the canonical property-based targets — arbitrary text in, no throw, and for `parseLearningsConfig` the additional invariant that every declared key resolves to either the configured value or its §4.1 default and never to `undefined`. Example-based coverage of a text parser is a known gap in this repository's standards. Fix: extend D-O-3 to oblige totality properties over all three, with `parseLearningsConfig`'s per-key fallback invariant stated explicitly. | DEC-LI-02 §Decision; D-O-3 |
| F-06 | Low | Process | **Four re-evaluation triggers cannot be detected by any test or monitor, and the document does not say so.** "Operators report unwanted injection in repositories that never opted in" (DEC-LI-07), "evidence that role compliance degrades when advisory context is last in the prompt" (DEC-LI-05), "a catalogue grows past the size where hand transcription is maintainable" (DEC-LI-10) and "the corpus grows past the point where per-dispatch re-reading is affordable" (DEC-LI-06) are all human-judgement triggers. That is legitimate, but mixing them undifferentiated with the mechanically detectable ones (DEC-LI-04's pinning test, DEC-LI-01's `MODULE_NAMES` edit) leaves a reader unable to tell which triggers will fire on their own. Fix: mark each trigger as *mechanically detected* (naming the oracle) or *review-time judgement*, and where a cheap proxy exists — corpus document count, catalogue member count — name the threshold so the judgement has an observable prompt. | DEC-LI-05, -06, -07, -10 §Re-evaluation triggers |

## Positive Observations

- Every code claim I re-derived at HEAD held. `MODULE_NAMES = ["orchestrate-dev.js", "orchestrate-queue.js"]` (`pdlc/engine/scripts/prepack.mjs:20`); `LS_FILES_ARGV` as a frozen argv over the two globs (`pdlc/workflows/consolidate-learnings.js:1338`); `defaultListFiles` returning basenames from one non-recursive `readdirSync` with directories filtered out (`orchestrate-dev.js:11586`); `WALK_SKIP_DIRS = new Set([".git", "node_modules"])` (`pdlc/workflows/lib/document-oracles.mjs:69`); the prompt composed as `` `${basePrompt}\n\n${PACING_CONTRACT_CLAUSE}\n\n${opener}` `` (`orchestrate-dev.js:8978`); `ADVISORY_DEFAULTS.enabled === false` (`orchestrate-dev.js:1944`). Grounding a DECISIONS document this densely is what makes it reviewable at all.
- The two claims most likely to be hand-waved were the two that most needed checking, and both are exactly right. `git check-ignore -v .baseline-worktree` exits non-zero here today, so DEC-LI-09's ignore obligation is real and not defensive. And Phase CR really does call `reviewLoop` with `docType: null` (`orchestrate-dev.js:14556`), which survives `roundDocType = docType === undefined ? docTypeFromPath(doc) : docType` (`:7306`) and reaches `dispatchAndVerify` as `docType: roundDocType` (`:7347`) — so DEC-LI-03's "the single-conjunct gate is not simpler in effect; it is wrong" is demonstrated, not asserted.
- The corpus count is right: the exact `LS_FILES_ARGV` pathspec returns **9** documents here, matching the Context section's claim. A number a reader can re-run in one command is worth more than a hedge.
- DEC-LI-07's five-state configuration table is set-equal to FSPEC v0.7 `BR-14`'s five states, row for row, including the `enabled: false` row's "no injection key at all — absent, not present-and-empty" distinction. Restating an upstream enumeration is usually where drift enters; this one is clean.
- DEC-LI-10 is the correct call for the right stated reason, and it names the failure it prevents (`X === X` passing for any edit, including a deletion) rather than appealing to convention. Making a catalogue addition a deliberate two-file edit is buying a reviewable diff, and the entry says so.
- "Stated honestly" in DEC-LI-08 and "Cost, stated plainly" in DEC-LI-06 are the two most useful paragraphs in the document: a design that names the sense in which it only *weakly* satisfies C-8, and names the unbounded term in its own cost model, is far easier to test against than one that claims completeness.
- The "Decisions deliberately NOT taken here" section, and the closing note that there is no retry ladder because retry would make E-32 depend on timing, both close off questions a downstream author would otherwise reopen. The retry note in particular is a testability argument, and a correct one.


## Recommendation

**Needs revision**

Three High findings gate this. All three are the same shape, which is worth naming: the document reasons better about oracle vacuity than almost any DECISIONS I have reviewed — it identifies the vacuous-green risk in a memo (DEC-LI-06), in a recomputed merge-base (DEC-LI-09), in a manifest that checks itself (DEC-LI-09), in a derived expected set (DEC-LI-10), and in a set-equality oracle that cannot see an omitted dispatch site (DEC-LI-03) — and then, in three of those five places, stops one step short of handing anyone the falsifying test. F-01 is different in kind and is the one to fix first: the `_git` never-throws claim is contradicted by `rtGit` at HEAD, and the design's whole enumeration-failure strategy is derived from it, so the fail-open guarantee would ship green and untested on the channel that actually runs the pipeline.

None of the three needs a design change. F-01 is a corrected Constraints row plus a rejecting-`_git` double; F-02 is two assertions added to a guard test that already exists in the design; F-03 is one row in the obligations table. The decisions themselves — attach once at `dispatchAndVerify`, no cache, no third module, suffix not insertion — are sound and well argued, and I would expect a v0.2 to be approvable.
