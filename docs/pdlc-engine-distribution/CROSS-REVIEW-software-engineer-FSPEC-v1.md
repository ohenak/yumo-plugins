| F-01 | High | Local | **F-5 depends on three publish blockers the FSPEC never names.** At HEAD `pdlc/engine/package.json` declares `"private": true` (`:4`), the unscoped name `pdlc-engine` (`:2`), and `"license": "UNLICENSED"` (`:11`) — M-ENG-11's measured facts, which the REQ prices at **O-8** as blocking the first publish. | F-02 | High | Local | **The publish flow is the only flow with no stated verification carrier, and its natural carrier is irreversible.** §5.1 and §5.2 each name a carrier that is "decidable offline" and AC-5.1's probe is explicitly "behind an injectable seam" — the document is otherwise disciplined about testability. F-5 is not: AT-3.1 (publishes), AT-3.3 (requires "version N published; its bytes hashed", then a re-run), and AT-3.5 (scans a published package) have no observable path that does not consume a real version on public npm, and npm's immutability — the very property C-7 selects the channel for — makes each rehearsal permanent (an unpublished version can never be republished). This is the cost half of my lens: the feature buys immutability and pays for it in untestability, and the FSPEC currently prices neither. Fix (either is sufficient, but one must be chosen here, not in the TSPEC): state at F-5 that the registry endpoint is a substitutable input so AT-3.1/3.3/3.5 can run against a local registry; **or** state explicitly that these three are one-time release-rehearsal observations against the real channel, accepting the burned version numbers, so the TSPEC does not discover the choice mid-implementation. | F-5; AT-3.1, AT-3.3, AT-3.5 |
| F-03 | Medium | Local | **Business-rule id collision between §4 and §5.** §4 declares `BR-5.1`…`BR-5.4` under "BR-5 — Provenance", while §5.1 declares `BR-5.1.1`…`BR-5.1.5` and §5.2 declares `BR-5.2.1`/`BR-5.2.2`. `BR-5.1.x` reads as a sub-rule of provenance's `BR-5.1`, which it is not, and the edge-case table cites both namespaces without disambiguation: E-23 cites `BR-5.1` meaning provenance, E-24 cites `BR-5.2`/`BR-5.3` meaning provenance, while E-19–E-22 cite `BR-5.1.3`/`BR-5.2.1` meaning §5. | F-06 | Medium | Local | **AT-6.1 asserts an exit code the shipped script does not give from an arbitrary tree.** F-7 step 2 and AT-6.1 assert that build, bare-path `sync-workflows.sh`, then `--check` "all three exit 0". Plain sync exits **2** whenever any manifest row measures `local-edit` or `unverified` (`pdlc/hooks/scripts/sync-workflows.sh:703-722`), and `unverified` is the state of *every* pre-existing consumer copy the first time the mechanism runs — i.e. of most operator machines. | F-08 | Medium | Local | **A conjunct of AC-2.1 is dropped in the flow that owns it.** AC-2.1's *Then* is three-part: the CLI is on `PATH`, **it reports its version triple (AC-1.4)**, and a pipeline command reaches the handshake. | F-09 | Medium | Local | **§5.3's set-equality is undefined for runs that do not produce all four kinds.** The rule says a dev-mode run's mark appears in "**exactly** these artifact kinds, checked by set-equality so an unmarked kind fails". A green single-feature run writes no POSTMORTEM (kind 2) and rewrites no `QUEUE.md` row (kind 3 — direct runs write that row only on halt, per the queue lifecycle). Read literally, such a run fails the equality for two kinds it could not have produced; read charitably, the oracle silently becomes "of the kinds this run produced", which is a containment check over an unstated set — the failure mode §5.2 explicitly rejects. AT-5.3 dodges this by constructing a run that writes all four, so the ambiguity survives review and lands in PROPERTIES. Fix: state the equality over *kinds the run produced*, and pair it with the positive that a run producing kind K unmarked fails. | §5.3; AT-5.3 |
| F-10 | Medium | Local | **The `[shipped]`/`[new]` discipline §3 declares is applied to two flows out of seven.** §3 states that a step describing behaviour not present at HEAD "is marked **[new]**" and shipped behaviour "is marked **[shipped]** with its symbol, so a reviewer can check the claim in one pass". F-1 and F-4 honour it; F-2, F-3, F-5 and F-7 carry no marks at all, F-6 states its newness only in prose. F-5 is the costly case: O-A measures that there is **no release automation of any kind** (`.github/workflows/` holds exactly one file, confirmed at HEAD), so all nine of its steps are new work, and an unmarked flow reads as though some of it exists. The convention is load-bearing for PLAN sizing, not cosmetic. Fix: mark every step in F-2, F-3, F-5, F-6, F-7 — the exercise will also surface which parts of F-2/F-3 are pure packaging versus pure documentation. | §3; F-2, F-3, F-5, F-6, F-7 |
| F-11 | Low | Local | **NG-6 is reconciled by rewriting it rather than by scoping it.** F-3 step 5 and BR-2.2 say consumer config is "read… and never written; reading is not writing (NG-6 forbids only the latter)". The gloss is inherited faithfully from the REQ's own O-2, so this is not a defect the FSPEC introduced; an erratum is raised against the REQ and this row records the FSPEC-side wording that would follow from it. Also note BR-2.2 sits under "BR-2 — Install and upgrade" while describing run-time behaviour. | F-3 step 5; BR-2.2 |
