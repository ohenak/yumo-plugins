Milestone 2 · Week 2

MVP 1: Feature to pull request

One local command takes an approved spec through implementation, tests, PR creation, required CI monitoring and bounded CI repair.

Workspace from M2: Continue this planning and delivery conversation in the yumo-plugins workspace. The regime-ledger repository is the external consumer experiment; the old GitHub Yumo repository is deprecated.
Mandatory result: Demonstrate the working capability on real repository code. A document, mock, or interface alone does not pass this milestone.

Start here

Workflow repository: yumo-plugins. External consumer: regime-ledger, with requirements and decisions in its GitHub Issues.

Inspect these paths first: pdlc/engine/; pdlc/workflows/orchestrate-dev.js; pdlc/workflows/runtime-adapter.js; pdlc/skills/ship-pr/

Dependency: Milestone 1 must have a passing run and a signed-off completion report.

Implementation steps

  1. Reuse the current engine CLI and merge/PR mechanisms. Add a thin command only if missing.
  2. Select a real low-risk feature. Run the full workflow with the current single-provider Claude configuration.
  3. Detect pending, green and red required checks for the current PR HEAD SHA.
  4. Return actionable CI failure evidence to the original author agent. Cap repair attempts per failure signature.
  5. Do not merge if any required check or policy gate fails. Allow manual merge at MVP stage.
  6. Capture the accepted spec, commit, PR URL and evidence in a compact completion report.

Exit tests

  • A new feature creates exactly one PR and receives a real CI outcome.
  • A controlled failing CI test is repaired and pushed once, with revalidation.
  • When repair fails, the run stops and reports a blocker; it never claims completion.
  • A second low-risk feature uses the MVP workflow, not a manual implementation path.

Agent session contract

Start gate: Check the previous milestone report and its real test evidence. Stop if the previous milestone has not passed. Never fabricate missing artifacts.

Task: Deliver a usable single-provider feature-to-PR workflow. Do not defer MVP completion to multi-model routing, SQLite or a web dashboard.

Time and token stop rule: Make the smallest change that can pass the exit gate. After two failed repair attempts for the same blocker, stop and report it. Do not continue into an unapproved refactor. Avoid drafting more than one speculative design before testing one real path.

Writing and evidence rules

  • Use short active sentences. Give technical terms one defined meaning.
  • Separate observed facts, assumptions and proposed changes.
  • Keep exact commands, paths, URLs and test references.
  • Never report PASS for an unrun check.
  • These rules adapt ASD-STE100 principles; they are not certified full compliance.
