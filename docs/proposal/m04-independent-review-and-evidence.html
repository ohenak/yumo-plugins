Milestone 4 · Week 4

MVP 3: Cross-provider model routing

Use GPT and Claude as separate selectable workers in personal projects, with independent findings linked to evidence.

Mandatory result: Demonstrate the working capability on real repository code. A document, mock, or interface alone does not pass this milestone.

Start here

Workflow repository: yumo-plugins. Consumer target: choose and document it in this milestone’s GitHub Issue; the old Yumo repository is deprecated.

Inspect these paths first: pdlc/workflows/runtime-adapter.js; pdlc/engine/; yumo environment config (if present)

Dependency: Milestone 3 must have a passing run and a signed-off completion report.

Implementation steps

  1. Define a minimal invoke-agent contract: model, role, working directory, input refs, limits, result and evidence refs.
  2. Add one GPT runtime adapter without replacing Claude execution.
  3. Configure personal allowlist GPT-6 and permitted Claude models; enterprise allowlist GPT-5.2 and Claude Opus 5.5.
  4. Fail closed on missing, disallowed or unapproved provider. No fallback across environment boundaries.
  5. Pin reviewer to a different model provider when available and authorized.
  6. Produce structured findings with source references and reproducible tests.

Exit tests

  • The Week 3 real feature-to-PR workflow succeeds with one GPT worker and one Claude reviewer (or vice versa).
  • An employer profile rejects a GPT-6 request without invoking that model.
  • An invalid provider/credential configuration stops safely.
  • Cross-model disagreement appears as an explicit finding, not a majority vote.

Agent session contract

Start gate: Check the previous milestone report and its real test evidence. Stop if the previous milestone has not passed. Never fabricate missing artifacts.

Task: Implement only the adapter methods used by the existing execution flow. No generic marketplace or speculative model registry.

Time and token stop rule: Make the smallest change that can pass the exit gate. After two failed repair attempts for the same blocker, stop and report it. Do not continue into an unapproved refactor. Avoid drafting more than one speculative design before testing one real path.

Writing and evidence rules

  • Use short active sentences. Give technical terms one defined meaning.
  • Separate observed facts, assumptions and proposed changes.
  • Keep exact commands, paths, URLs and test references.
  • Never report PASS for an unrun check.
  • These rules adapt ASD-STE100 principles; they are not certified full compliance.
