Milestone 3 · Week 3

MVP 2: Independent model review

The PR author repairs findings from a different reviewer agent. Two reviewer passes maximum.

Mandatory result: Demonstrate the working capability on real repository code. A document, mock, or interface alone does not pass this milestone.

Start here

Workflow repository: yumo-plugins. Consumer target: choose and document it in this milestone’s GitHub Issue; the old Yumo repository is deprecated.

Inspect these paths first: pdlc/workflows/orchestrate-dev.js; pdlc/engine/; pdlc/skills/se-review/; pdlc/OPERATIONS.md

Dependency: Milestone 2 must have a passing run and a signed-off completion report.

Implementation steps

  1. Keep the working Week 2 feature-to-PR path.
  2. Use separate agent sessions and a separate reviewer context; use distinct model families if already accessible, but do not block on adapter framework.
  3. Give reviewer the spec, PR diff and test evidence; do not give author self-approval.
  4. Run reviewer pass 1; original author fixes findings; run pass 2 only when required.
  5. After pass 2, unresolved High/Critical findings block merge and escalate. No silent approval.
  6. Record model identity, pass number, finding identifiers, fixes and evidence.

Exit tests

  • Exactly two or fewer independent reviewer passes per PR review episode.
  • A seeded critical defect blocks the PR after pass 2 if not fixed.
  • A repaired defect is verified by tests and the independent reviewer.
  • Use the Week 2 workflow to build this milestone and report saved human minutes.

Agent session contract

Start gate: Check the previous milestone report and its real test evidence. Stop if the previous milestone has not passed. Never fabricate missing artifacts.

Task: Add independent verification to the existing usable path, not a separate framework. Distinguish multiple agent roles from multiple model providers.

Time and token stop rule: Make the smallest change that can pass the exit gate. After two failed repair attempts for the same blocker, stop and report it. Do not continue into an unapproved refactor. Avoid drafting more than one speculative design before testing one real path.

Writing and evidence rules

  • Use short active sentences. Give technical terms one defined meaning.
  • Separate observed facts, assumptions and proposed changes.
  • Keep exact commands, paths, URLs and test references.
  • Never report PASS for an unrun check.
  • These rules adapt ASD-STE100 principles; they are not certified full compliance.
