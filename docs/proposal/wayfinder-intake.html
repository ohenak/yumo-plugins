Requirements and design · Draft workflow · 2026-10-14

Work out requirements and design with Wayfinder

You bring a proposed capability. Wayfinder helps you settle its requirements, design, and decisions. GitHub Issues keeps the record.

What each part does

You

Propose a feature or outcome. Decide its scope, behavior, and trade-offs during the conversation.

Wayfinder

Checks facts, asks clear questions, and records the resulting requirements, design, and decisions in GitHub Issues.

PDLC delivery

Builds from the accepted issue record. It links its commits, tests, review, PR, and CI evidence back to that record.

This design adapts the decision-map method in Wayfinder and the question rounds in Grilling. The draft Yumo skill applies the clear-communication rules.

From a proposed feature to delivery

  1. Start with your candidate. The feature may come from you, an existing issue, or a useful idea from older code. Wayfinder does not choose it for you.
  2. Check facts and open questions. Wayfinder reads the target repository and relevant issues. It asks you to decide behavior and trade-offs that facts cannot settle.
  3. Record requirements and design. GitHub Issues holds the expected behavior, acceptance checks, design options, chosen approach, and reasons.
  4. Confirm the handoff. Wayfinder reads back the result. Your correction or acceptance is recorded in the issue. Open blocking decisions stay visible.
  5. Build and verify. PDLC uses the accepted issue record as its source. It may make local working copies for implementation, but links the delivered evidence back to Issues.

GitHub Issues is the default record

Use the feature’s target repository. pdlc --help issue #86 lives in ohenak/yumo-plugins. The report experiment issue #1 lives in ohenak/regime-ledger. Link issues across repositories when one decision affects both.

For a small feature, one issue can hold the requirement, design, decisions, and handoff. For a broad effort, use a short map issue with linked decision issues. Create separate issues only when different questions need different owners or dependencies.

Track scope, acceptance checks, alternatives, answers, rejected directions, research, and prototype links in Issues. If GitHub is unavailable, keep a pending conversation summary. Do not claim the record is ready or silently move it to local Markdown.

Make the conversation easy to follow

  • Start each round with one sentence about the proposed feature and what is already decided.
  • Ask only questions whose prerequisites are settled. Group independent questions when the group remains easy to read.
  • Give each question a clear title, a short reason, useful choices, and a recommendation with its trade-off.
  • Check repository facts directly. Ask you for decisions, not facts the agent can find.
  • After each reply, restate the decisions in plain words and name what remains open.
  • Use one term for one concept. Define unfamiliar terms and preserve the difference between “must,” “may,” and “usually.”

These rules retain Wayfinder's decision-tree method and apply clear-communication to every question, answer summary, and issue update.
