Use past runs to simplify delivery

Start with a user-proposed capability. Use Wayfinder to settle requirements and design in GitHub Issues. Prove that the delivery engine can complete that work in an external project.

Recommended direction

Keep the proposal's milestone order. Move real use in a consumer project into M2. A successful pdlc doctor call only proves startup. M2 must finish a feature and produce a PR with test and CI evidence.

The draft Yumo Wayfinder skill gives the user control of feature choice. Its decisions and accepted feature briefs live in GitHub Issues. A delivery agent must not turn its own convenient test idea into a product feature.

The deliver-feature-chain skill simplifies control: one gatekeeper checks work before it proceeds. It still asks for many documents. Carry its proof checks into the engine. Scale the document set to the feature's risk.

Portable small-feature contract

An operator should supply a repository, an accepted Wayfinder feature brief, a test command, and branch or PR policy. Startup checks should name the engine and plugin versions, available credentials, missing permissions, planned writes, and external actions.

Each run should produce one evidence manifest. Record the brief, requirement, commits, PR, agent identities, commands, tests, and CI result. Also record review findings, elapsed time, human minutes, cost or UNKNOWN, and any stop reason.

  1. If the same blocker fails twice, stop and keep its evidence.
  2. If a provider, credential, approval, or repository policy is unavailable, do not substitute another one without authorization.
  3. Before marking work complete, verify that the requested artifact exists and passes its direct check.
  4. After a repair, check the current commit. Do not reuse an older green result.
  5. Where repository policy requires human review, keep that gate.
