Milestone 8 · Weeks 9–10; reserve Weeks 11–12

Pilot: The system builds its next features

Prove three real features can move from approved spec to verified PR and a safe Terraform release with less human effort.

Mandatory result: Demonstrate the working capability on real repository code. A document, mock, or interface alone does not pass this milestone.

Start here

Workflow repository: yumo-plugins. Consumer target: choose and document it in this milestone’s GitHub Issue; the old Yumo repository is deprecated.

Inspect these paths first: yumo-plugins and yumo; manifests and actual CI/GCP output

Dependency: Milestone 7 must have a passing run and a signed-off completion report.

Implementation steps

  1. Choose three production-representative low-risk features, including one for the harness itself.
  2. Run baseline/manual and MVP-driven workflows on comparable tasks.
  3. Test normal path, failing CI, interrupted run, rejected model review, enterprise approval simulation and staging rollback.
  4. Calculate verified feature cost, human minutes, PR wait time and escaped defects.
  5. Remove redundant code and postpone unused infrastructure.
  6. Produce a prioritized backlog only from observed limitations, not speculative scalability concerns.

Exit tests

  • At least three features complete the full supported lifecycle with evidence.
  • Each feature has a real PR and green mandatory checks.
  • No high/critical defects remain open at release and no policy bypass occurs.
  • A 21-day unattended travel test is a later maturity goal, not an MVP exit gate.
  • Founder evaluates actual saved time and elects whether to advance to broader autonomy.

Agent session contract

Start gate: Check the previous milestone report and its real test evidence. Stop if the previous milestone has not passed. Never fabricate missing artifacts.

Task: Finish with working evidence, operational runbook, and measured effort. Avoid declaring success based on unit tests alone.

Time and token stop rule: Make the smallest change that can pass the exit gate. After two failed repair attempts for the same blocker, stop and report it. Do not continue into an unapproved refactor. Avoid drafting more than one speculative design before testing one real path.

Writing and evidence rules

  • Use short active sentences. Give technical terms one defined meaning.
  • Separate observed facts, assumptions and proposed changes.
  • Keep exact commands, paths, URLs and test references.
  • Never report PASS for an unrun check.
  • These rules adapt ASD-STE100 principles; they are not certified full compliance.
