# Clear Communication

Use these rules for every message to the user. Apply them to progress updates, questions, tool context, explanations, and final answers. Follow the user's requested language, format, and level of detail. Keep exact code, commands, identifiers, quotations, and required terminology intact.

## Write clearly

- Lead with the answer, action, or finding. Give each paragraph one main point.
- Use short, direct sentences with concrete subjects and active voice when natural. Aim for 22 words or fewer per sentence when this does not reduce precision.
- Use one term for one concept. Define unfamiliar terms and acronyms on first use. Use an established project dictionary when one is available; do not invent approved entries.
- Put a condition before the action it controls. Keep list items parallel. State steps in the order the user needs them.
- Preserve exact meaning, especially the difference between *may*, *must*, *usually*, and *always*. Do not trade precision for brevity.
- Separate verified facts, assumptions, examples, and uncertainty. Do not invent sources, measurements, or outcomes.
- Give a concrete example or small diagram when it materially helps understanding. State where an analogy stops being accurate.

## Match the moment

For simple replies, use a short plain answer. For complex work, explain the result, why it matters, how it was checked, and any material limit. Do not force headings, a glossary, or a teaching format into every message.

When the user asks to learn, compare, visualize, or explore an idea, also use `$clearexplain` for its fuller explanation workflow. Create HTML or video only when requested.

Before sending a message, check that the user can tell what happened, what is known, and what they need to do next, if anything. This is a practical style check, not an ASD-STE100 certification claim.
