## Findings

| ID | Severity | Scope | Finding | Requirement ref |

| F-01 | High | Local | **`schemaVersion` does not appear anywhere in the TSPEC.** The string is absent from §3.3's public surface, §4.1's metric types, §4.2's `StatsOutcome`/`StatsReport`, and every oracle in §6. REQ-STATS-02 makes "one schema-version field" one of only two observable guarantees the P0 machine-readable mode owes its callers, and FSPEC BR-24 fixes it as an integer, `1` at first release, whose presence is REQ R-5's stability anchor (FSPEC BR-21, BR-23, BR-24, BR-30). The design as written has no type that can carry it and no test that would notice its absence. **Fix:** name `schemaVersion` in the JSON contract (a `renderJson` obligation, not a `StatsReport` field, since both renderers share one report value), and add it to §6.3's cross-mode oracle's asserted key set. | REQ-STATS-02, FSPEC BR-21/BR-23/BR-24 |
| F-02 | High | Local | **The JSON top-level key set is never stated, and the type that reaches `renderJson` carries two keys BR-21 forbids.** §3.3 types `renderJson(outcome: StatsOutcome): object` with no key set; §4.2 makes it a total pure function of `StatsReport`, whose `kind: "single"` arm is a bare `FeatureStats`; and §4.1's `FeatureStats` carries `feature` and `dir` alongside the four metrics. FSPEC BR-21 says the single-feature document has "exactly five top-level keys: `schemaVersion`, `reviewRounds`, `dodRounds`, `halts`, `byteRatio`" and states explicitly that "the feature name is not echoed as a top-level key"; BR-23 says a fleet `features` entry is "BR-21's document minus its hoisted `schemaVersion`", i.e. `dir` is excluded there too. The TSPEC never names the projection from `FeatureStats` to the emitted object, so the straightforward implementation of the document as written serialises `feature` and `dir` and breaks REQ-STATS-02's set-equality on day one. §6.3's cross-mode oracle does not close this: `dir` feeds BR-17's human header (per §4.1's own comment), so an oracle comparing "the human table's metric set" to "the JSON key set" has no reason to reject it. **Fix:** state the emitted key sets — five for single-feature, three for fleet, three for the error object — in §4.2 as an explicit contract, and have §6.3 assert them by set-equality against a literal transcription of BR-21/BR-23/BR-30 rather than deriving them from `FeatureStats`. | REQ-STATS-02, FSPEC BR-21/BR-23 |
| F-03 | High | Local | **`NON_FEATURE_DIRS` is never asserted set-equal to the `docs/` root's actual non-feature directories.** REQ-STATS-07 fixes the eight-member exclusion set and requires it be "asserted set-equal, so a directory added later fails rather than silently joining the report"; FSPEC BR-26 restates this as "checked set-equal" and AT-19 is its acceptance test. The TSPEC discharges it with prose — §4.4: "All eight are present at this repository's `docs/` root today, and they are exactly the non-feature directories there" — which is a measurement, not an assertion. §6.4 enumerates exactly four anti-drift oracles (parser identity, doc-type catalogue, vendoring co-change, no-write capability); none is this one. §6.2's level table lists `discoverFeatures` under "Unit — pure" with no set-equality obligation, and AT-19 is named nowhere in §6 (only in §8.3, as inherited circularity). A containment-only test over `NON_FEATURE_DIRS` passes when a ninth non-feature directory appears, which is the exact regression REQ-STATS-07 exists to prevent. **Fix:** add a fifth oracle asserting set-equality between `NON_FEATURE_DIRS` and the non-feature directory names at the repository's `docs/` root, and map AT-19 to it in §6. | REQ-STATS-07, FSPEC BR-26 |
| F-04 | High | Local | **§6.4's doc-type catalogue oracle cannot function as written: it probes an invalid role slug.** The oracle is specified as `parseReviewFilename("CROSS-REVIEW-se-review-{T}-v1.md")`-shaped input, asserting the six rows stay accepted and the known-rejected `REVIEW` stays rejected. But `se-review` is a *key* of the driver's `MAP` (`pdlc/workflows/orchestrate-dev.js:10037-10040`), not one of its values; the closed role catalogue the grammar validates against is `REVIEWER_ROLE_SLUGS = Object.values(MAP)` (`orchestrate-dev.js:10044`), i.e. `software-engineer` / `product-manager` / `test-engineer`, and `parseReviewFilename` rejects anything else with `bad_role` before it ever reaches the doc-type check (`orchestrate-dev.js:10143`). So every one of the six probes returns `{ok: false, reason: "bad_role"}`, and the "`REVIEW` stays rejected" half passes for the wrong reason. This matters in the product lens because §3.3 justifies keeping `REVIEW_DOC_TYPE_ROWS` as a *local* constant rather than an import precisely by pointing at this oracle — "so 'local constant' does not mean 'free to diverge silently'". With the oracle inoperative, BR-09's six-row set and its ordering — an observable of every REQ-STATS-01 and REQ-STATS-03 report — can drift from the driver's catalogue with nothing going red. **Fix:** use a real role slug in the probe and assert both halves by set-equality over the six accepted types, not by containment. | REQ-STATS-03, FSPEC BR-09 |
| F-05 | Medium | Local | **§4.3 attributes to BR-11 wording BR-11 does not carry.** The TSPEC writes: "`n > 0` is exactly BR-11's 'no `CODE_REVIEW-{feature}-v{N}.md` file matching the version grammar remains'". FSPEC BR-11 actually reads "no `CODE_REVIEW-*` file remains in the directory"; the version-grammar qualifier is REQ-STATS-04's, not BR-11's. The chosen behaviour is the REQ-faithful one, so the code is right and only the citation is wrong — but the misquote hides a genuine REQ/FSPEC divergence (a `CODE_REVIEW-{feature}-draft.md` or a foreign-feature `CODE_REVIEW-` file left behind after harvest makes the two readings disagree). **Fix:** cite REQ-STATS-04 for the grammar-matching reading and note that BR-11's wording is looser; the divergence itself is routed as an FSPEC erratum. | REQ-STATS-04, FSPEC BR-11 |
| F-06 | Medium | Local | **The ratio's harvested test silently picks one of two readings of BR-16 without saying so.** §4.3 computes `crossReviews = basenames.filter(b => parsers.parseReviewFilename(b).ok)` and then tests `harvested && (crossReviews.length === 0 || dodReviews.length === 0)`. FSPEC BR-16's condition is phrased over `CROSS-REVIEW-*` files, not over grammar-passing ones. The two readings disagree on a shape this repository's archive actually produces: `docs/completed/pdlc-advisory-wave-gate/` carries four `CROSS-REVIEW-{product-manager,test-engineer}-REVIEW-v{1,2}.md` files, which §4.3 itself classifies as malformed and sizes into neither side of the ratio. A post-harvest directory left holding only such files plus `LEARNINGS-*.md` reports `harvested` under the TSPEC and `measured` under BR-16's literal text — a difference an operator reading the ratio would act on. **Fix:** state the chosen reading explicitly in §4.3 and cite the REQ-STATS-06 clause that settles it; the FSPEC ambiguity is routed as an erratum. | REQ-STATS-06, FSPEC BR-16 |
| F-07 | Medium | Local | **The leading-underscore discovery predicate is a product decision taken in an engineering artifact, and its acknowledged residue is the behaviour REQ-STATS-07 forbids.** §4.4 adopts `name.startsWith("_")` as the unclassified discriminant and states the residue plainly: a future bare-named non-feature directory "would be reported as a feature with zero-state metrics". REQ-STATS-07's whole point is that a directory added later must surface rather than "silently join the report", so for the bare-named case the criterion's protection is not delivered. Routing the missing FSPEC predicate as an erratum (§8.3) is the right channel and is credited below; what is missing is that the TSPEC nonetheless commits to the invented predicate as the shipping behaviour rather than marking it provisional on the erratum's resolution. **Fix:** mark §4.4's predicate as provisional pending the FSPEC erratum, and name the observable the design will adopt if the FSPEC answers differently. | REQ-STATS-07, FSPEC BR-26 |
| F-08 | Low | Local | **§7.1 collapses BR-21, BR-22, BR-23 and BR-24 into a single traceability row** (`renderJson` over `StatsReport`; `FeatureResult`'s discriminant → §4.1, §4.2). That lumping is what let F-01 and F-02 pass unnoticed: neither of REQ-STATS-02's two observable guarantees — top-level key-set equality, and the presence of a schema-version field — has a row of its own naming the component that discharges it. **Fix:** give BR-21, BR-23, BR-24 and BR-30 one row each, each pointing at a named contract in §4.2 and a named oracle in §6. | REQ-STATS-02, FSPEC BR-21/BR-24 |
