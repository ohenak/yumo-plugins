| F-01 | High | Local | **The skip discipline's un-skip owner is underdetermined for two case groups, and each one halts a wave when its 🟢 owner un-skips too early.** §3 preamble step 2 says each 🟢 task's only edit is to "delete `.skip` from its own block" in **its** named test file, and §5.2's batches 7–17 gate asserts "that block passes in full". That works only if the block's un-skipper is the task that lands the *last* symbol its cases need. Two groups violate it. **(a) T-03-6(b).** §8.2's new gate-row expansion names the 🟢 owners as "A-23, A-24 (🟢 owners of the seams' gates)", but the cases live in `advisoryDriver.test.js`, whose *only* declared green owner anywhere in the PLAN is A-22 (§3's Test File column, §8.1's T-03 row, §4's manifest) — A-23's and A-24's rows name `advisoryDodSeams.test.js` and `advisoryPubSeam.test.js` and nothing else. So §8.2 and §8.1 contradict each other about who un-skips, and an A-22 agent (batch 9, i.e. before A-23 at 10 and A-24 at 11) reading §3 will un-skip the whole file including the per-seam gate cases for A3/A4/A5 — which then fail, and `orchestrate-dev.js:8113-8118` halts the run. Note also that AC-4.5's five gate rows include A1 and A2, whose `verifyGate`s are implemented in `orchestrate-queue.js` by A-30/A-31 — neither is named as an owner at all. **(b) T-02-4 / T-02-5.** §3 A-05 puts them in `advisoryVerdict.test.js`, un-skipped by A-19 at batch 6. But FSPEC:287 defines T-02-4 as "exactly `attemptBudget` attempts made, seam escalates" and FSPEC:288 defines T-02-5 as an in-flight attempt preempted at the bound — both are the driver's attempt loop, and §3's own A-22 row (batch 9) claims "`Promise.race` preemption on injected `_now`/`_sleep`" as A-22's work. A-19 structurally cannot make them pass at batch 6. This is the same failure my v1 F-01 was about, reintroduced through §8.2's expansion and A-05's rewording. **Resolution:** state the rule explicitly — a `describe.skip` block's un-skipper is the task landing the last symbol the block's cases exercise — then (a) give `advisoryDriver.test.js` the extra green owners in §3's Test File column, §4's manifest and §8.1's row (or move T-03-6(b)'s per-seam gate cases into `advisoryDodSeams`/`advisoryPubSeam`/`advisoryQueueSeams`, which already carry the right owners), and (b) either move T-02-4/T-02-5 to `advisoryDriver.test.js` or add A-22 as a second green owner of `advisoryVerdict.test.js`. | §8.2 T-03-6 row; §3 A-05/A-07/A-22/A-23/A-24; §8.1 T-02 and T-03 rows |

| F-03 | Medium | Local | **§6.5's P-4 is not well-typed against the function it constrains, so it cannot be written as stated.** P-4 says `classifyEnvelope` is "idempotent (`classify(classify(x).ctx) === classify(x)`)". TSPEC §5.1 (`TSPEC-pdlc-advisory-tier.md:517`) declares `classifyEnvelope(candidate, ctx)` returning `{ inside: boolean, reason: string\|null, matched: string[] }` — the return carries no `ctx`, and the function takes two arguments, so the composition in the law does not type-check. The second conjunct has the same slip: "its result is always a member of `ADVISORY_REFUSAL_REASONS ∪ {null}`" is true of `.reason`, not of the result object. A property an implementer must reinterpret is a property an implementer will improvise — which is the drift §6.5 exists to prevent, and §9.2's checkbox ("all nine §6.5 properties exist") cannot be ticked against an unwritable law. **Resolution:** restate over the real signature — e.g. *determinism/purity*: for any generated `(candidate, ctx)`, two calls return deep-equal results and neither argument is mutated (a genuine falsifier for a classifier that memoises into `ctx`); plus *closure*: `result.reason ∈ ADVISORY_REFUSAL_REASONS ∪ {null}`, and `result.inside === (result.reason === null)`, which is the invariant a wrong implementation actually breaks. | §6.5 P-4 |
