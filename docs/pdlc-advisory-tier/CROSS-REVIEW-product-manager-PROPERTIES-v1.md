| F-01 | High | Local | **The operator's own envelope lever has no property.** AC-1.7 declares `advisory.envelope` an operator-owned knob defaulting to "the AC-3.3 allow-list", and AC-3.1 makes the envelope "declared in configuration as an explicit per-seam allow-list" — that configurability is the whole of US-03 ("a hard, declared boundary … un-widenable by the agent"). Every envelope property in §6 is written against the **default** set: PROP-ENV-12 pins `ENVELOPE_DEFAULTS = {E-1,E-2,E-3,E-4}` against a transcribed literal; PROP-CFG-07 asserts only that `config.envelope` is not *mutated* at runtime; PROP-LIFE-04 refuses a `withinEnvelope: true` claim "the configured envelope excludes" but never varies the configuration away from its default; PROP-A5-04/05/06 vary `ctx.permittedActions` by capability probe, explicitly **not** by config. Nothing in the document falsifies an implementation that reads `ENVELOPE_DEFAULTS` and ignores the parsed `config.envelope` entirely — such a build passes §4.1, §6.1 and §12.1's AC-3.1 row unbroken, and the operator's only narrowing lever is silently dead. **Fix:** add a property (home `advisoryEnvelope.test.js` or `advisoryDriver.test.js`) that parses a **narrowed** `advisory.envelope` — e.g. `["E-1"]` — and asserts positively that an otherwise-decidable E-2 candidate classifies `inside: false` with reason `out-of-envelope` plus O-1, while the E-1 candidate still classifies inside on the same fixture (so the property cannot pass by refusing everything). Add it to §12.1's AC-3.1 and AC-1.7 rows and to §12.2's A-06/A-20 rows. | AC-3.1, AC-1.7, US-03 |
| F-02 | High | Local | **E-2's decidable rule is the one AC-3.3 rule with no property.** AC-3.3 gives each permitted action a decidable rule, and the document proves three of the four: E-3 by PROP-ENV-11 (`branchCreated` true iff absent from the merge-base tree **and** from the default-branch tip — both conjuncts), E-4 by PROP-A2-02/03 (symbol still exists), E-1 by O-3's counted oracle (re-run on a sha byte-equal to the pre-seam head) plus PROP-A5-07 (push-free). E-2's rule — *the same check passes at **both** the merge-base commit **and** the default-branch tip, and fails at the branch head* — is asserted nowhere. PROP-A5-03 asserts only the **ordering** (the default-branch probe runs before the introduced test); PROP-A5-04 asserts the BL-05-absent path. An implementation that tested only the default-branch tip, omitting the merge-base conjunct, satisfies every property in §8.3 and §12.1's AC-3.3 row. This matters more than the other three rules because E-2 is the sole envelope member that lets the tier **commit and push** to the branch unattended. **Fix:** add a property to `advisoryPubSeam.test.js` (or `advisoryEnvelope.test.js`) asserting E-2 membership requires all three conjuncts, with one fixture per dropped conjunct — check failing at merge-base ⇒ out of envelope; check failing at default tip ⇒ pre-existing escalation (already PROP-A5-03); check passing at branch head ⇒ `conditionHolds` false — each paired with a positive in-envelope control. Register it in §12.1 under AC-3.3 and in §12.2 under A-11/A-24. | AC-3.3 (E-2) |
| F-03 | High | Local | **PROP-GATE-01…05 is an absence-only oracle, and §12.1 does not carry AC-4.5 into AC-4.6/NFR-2.** AC-4.6 quantifies over "AC-4.1 through **AC-4.5**": each must have a failing test proving the prohibition *and* "asserts the AC-3.6 positive triple on the same path — a negative assertion alone is satisfied by accident". PROP-GATE-01…05 (§6.5) states only "with the gate stubbed to fail the disposition must never be `resolved`" — satisfied by a thrown error, by `no-action`, or by an unset field. The mutation clause ("replacing the gate with `async () => ({ passed: true })` must make the case fail") proves the gate is *consulted*; it does not supply the positive outcome AC-4.6 demands. Correspondingly, §12.1's `AC-4.6` row lists only PROP-PROH-01…04 and its `NFR-2` row likewise, so AC-4.5's membership in AC-4.6's range is dropped from the matrix even though §12.1's own AC-4.5 row names PROP-GATE-01…06. **Fix:** restate PROP-GATE-01…05 as "the disposition must be `escalated` with reason `post-action-verification-failed`, satisfying O-1 in full" (the exact reason AC-3.6 row 4 assigns to a failed post-action gate), keeping the mutation clause as the second conjunct; then add PROP-GATE-01…05 to §12.1's AC-4.6 and NFR-2 rows. | AC-4.5, AC-4.6, NFR-2 |
