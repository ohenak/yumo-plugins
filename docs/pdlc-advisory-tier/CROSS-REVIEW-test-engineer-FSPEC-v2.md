## Findings

Seven, all new, all in sections this revision changed: one High, three Medium, three Low. The shape
is consistent — the revision added six new rules (V-5's carve-out, A5-3's cadence exclusion, A5-8,
A5-9, H-2b, H-3's channel clause) and gave four of them a test, so the findings are about the two
that landed without one, plus one rewritten oracle that can no longer fail.

| ID | Severity | Scope | Finding | Section ref |
|----|----------|-------|---------|------------|
| F-01 | High | Local | **T-10-3's rewritten expected value is derived from another run of the same code, so as written the oracle cannot fail.** D-6 now reads "the set of files a disabled run creates is **equal** to the set a run of the pipeline **without this feature** creates" — a comparison against pre-feature code, which is a real, falsifiable oracle. T-10-3 does not say that: its Given is "the tier disabled" and its Then is "the set of files the run created equals the set a **tier-off baseline run** creates". A tier-off run *is* the run under test, so the assertion compares a run's created-file set with its own — a tautology that passes whatever the feature creates, which is exactly the widening D-6 exists to catch and exactly what my v1 F-12 asked to close. Even under the charitable reading (that "baseline" means D-6's pre-feature pipeline) the expected value is still *computed by running code*, not transcribed: a fixture that re-derives the baseline from the same tree echoes the implementation and moves with it. **Resolution:** make the expected set a literal in the document — enumerate the created-file set of a pre-feature run in §12.1 (or pin it as "the set at commit `{sha}`, transcribed"), and restate T-10-3's Then as equality against that enumerated literal, with the failing direction named ("a file outside the enumerated set appears → red"). A set-equality whose right-hand side is produced by the system under test is not a set-equality. | §12.1 D-6, §12.3 T-10-3 |
| F-02 | Medium | Local | **V-5's new rollup-wait exclusion has no falsifying test, and §14.2 still maps NFR-4 to a test that cannot fail for it.** V-5 gained "Time spent waiting on GitHub's check rollup does not count against it (§9.2 A5-3)", and A5-3 gained the same rule with its rationale. §14.2's NFR-4 row was updated to *describe* the carve-out but its Tests cell is still `T-02-5` — a first-and-only-attempt overrun with no rollup in it, which passes identically whether or not rollup time is excluded. T-07-6 is the only test that could discriminate (an implementation that counted rollup wait would end the invocation after **one** cycle, failing "exactly that many cycles occurred"), but only if its fixture makes each re-poll wait exceed `seamBudgetMinutes` — and T-07-6's Given says nothing about elapsed time, so a fixture with instantaneous polls satisfies it under both implementations. The carve-out is load-bearing: A5-3 itself argues that without it "the shipped 10-minute default would end every A5 invocation inside its first attempt and `attemptBudget` would never bind", which I confirmed is arithmetically live (`dev:34` — the completion window is 30 min, three times the seam budget). **Resolution:** add one A5 test whose re-poll waits exceed `seamBudgetMinutes` while the fix work itself does not, asserting that the invocation reaches its full `attemptBudget` cycles and does **not** escalate `budget-exhausted` on the first, and pair it with the positive terminal state; then cite it in §14.2's NFR-4 row alongside T-02-5. (See also the ERRATUM: REQ NFR-4 defines the bound as unqualified wall-clock "measured from dispatch to verdict", which this carve-out contradicts.) | §4.3 V-5, §9.2 A5-3, §14.2 NFR-4 row |
| F-03 | Medium | Local | **§9.3's two completion-cap rows now describe opposite outcomes, and only the halting one has a test — so the behaviour-changing one cannot go red.** The revision split the old single row into "Checks register and then never complete **before any seam fired**" → A5-9, halt, seam does not fire (tested by the new T-07-10) and "A re-poll **inside** an A5 invocation hits the completion cap" → A5-3, consumes an attempt, escalate on budget (no test). The second is a genuine change to today's control flow, not a restatement: at `dev:6267-6272` the cap throws `haltError` from inside the poll loop, so "consumes an attempt" requires that throw to become a returnable condition when an advisory invocation is driving the poll. With no test on that path, an implementation that simply lets the existing halt propagate satisfies every test in §9.4 — T-07-6's cycles all end **red**, not **capped**, and T-07-10 asserts the halt, so both are green under the wrong behaviour. **Resolution:** add T-07-11 — given an A5 invocation whose first re-poll reaches the completion cap and whose second cycle then completes red, assert that the run did **not** halt at the cap, that exactly two attempts were consumed, and that the terminal disposition is `escalated` with reason `budget-exhausted` (positive conjuncts, so a propagated halt fails on the first). | §9.2 A5-3/A5-9, §9.3 (two cap rows), §9.4 |
| F-04 | Medium | Local | **H-3's new "goes through the channel the guard covers" clause is the whole point of the rule and no test drives the production path.** H-3 now says the distil step's delete "goes through the channel the guard covers rather than around it — the guard is the control, not a courtesy". That clause is necessary because the guard is a PreToolUse **Bash** hook that matches only `rm` / `unlink` / `git rm` inside `tool_input.command` (`guard-harvest-before-delete.sh:36`, registered at `hooks/hooks.json:9`); a distil step that removes the file by any other channel is silently unguarded. But T-08-4's Given is a bare "attempt to delete `ADVISORY-{feature}.md`" with no actor named, so it is satisfiable by a fixture that shells out an `rm` directly — the classic builder-not-wired green, proving the guard works while proving nothing about the code that will actually do the deleting. §10.5's edge row ("the distil step runs but `LEARNINGS-{feature}.md` does not exist") is the reachable version and carries no test id. **Resolution:** re-Given T-08-4 on the production path — *given a completed run reaching the distil step with no `LEARNINGS-{feature}.md` present* — and assert the three positives: the refusal is emitted, `ADVISORY-{feature}.md` still exists with its entries intact, and the run report names the refusal. Keep the direct-delete case as a separate, explicitly unit-scoped guard test if it is wanted, labelled the way T-04-3b now is. | §10.2 H-3, §10.5, §10.6 T-08-4 |
| F-05 | Low | Local | **T-08-10's per-seam half is unwritable because the Given does not say which seams the three invocations belong to.** The Then demands "the four counters are 3 / 1 / 1 / 1 by literal value **and** `invocations == resolved + escalated + no-action` holds **per seam** and in total". The literals 3/1/1/1 are the run totals; the per-seam rows are determined only once the Given fixes which seam produced each invocation (three seams → three 1/…/… rows; one seam → one 3/1/1/1 row). **Resolution:** name the seams in the Given (e.g. A3 `no-action`, A4 `resolved`, A5 `escalated`) and state the five per-seam rows as literals too, so the whole summary table is a transcription. | §10.6 T-08-10 |
| F-06 | Low | Local | **T-04-3b names the adjudicator as the unit under test but asserts a rule the adjudicator does not own.** A1-2 was correctly re-worded to "may never be **honoured**" — the honouring is the pipeline's, per BR-1. T-04-3b's Given is "the A1 adjudicator alone, fed a candidate whose pre-check result is blocked · When it returns `run-candidate` · Then the verdict is not honoured and the seam escalates", which leaves the component that refuses the verdict unnamed; a test author could reasonably put the assertion inside the adjudicator, where BR-1 says it must not live. **Resolution:** re-Given on the honouring seam ("the A1 seam's verdict handler, given a pre-check result of blocked and an adjudicator verdict of `run-candidate`"), so the test pins the control rather than the proposer. | §6.3 A1-2, §6.6 T-04-3b |
| F-07 | Low | Local | **H-2 states an operator-visible consequence for Phase MERGE and no test pins it, nor the literal it produces.** H-2 now says the post-PUB distil commit leaves "the branch head Phase MERGE evaluates … one commit beyond the checked head" and that an operator with merges enabled "should expect a deferral on runs where a seam fired". I confirmed the mechanism: `ciRule` at `dev:759-784` maps a `pending` rollup to `{result:"refused", row:"10", reason:"CI is pending", escalate:false}` — so the outcome is a **non-escalating** refusal on row 10, with no `MERGE ESCALATION:` notice, which H-2's "defers or refuses with its existing notice" slightly overstates. T-08-3 asserts the commit and the push but stops at the PR. **Resolution:** either add a test asserting that on a seam-fired run with merges enabled `mergeStatus` is not `merged` and the report carries the row-10 reason literal, or state explicitly in H-2 that the Phase MERGE consequence is out of scope for this FSPEC's tests, and correct "with its existing notice" to name the non-escalating path. | §10.2 H-2, §10.6 T-08-3 |
