## Findings

| ID | Severity | Scope | Finding | Section ref |
|----|----------|-------|---------|------------|
| F-01 | High | Local | **The post-PUB distil step has no specified relationship to the PR it is deleting files behind.** §10.2 H-1 moves the record's distil-and-delete after Phase PUB. But Phase PUB is where the PR is raised (B-15), and Phase MERGE — which merges that PR — runs after it (`dev:8274`). `dev:8249-8250` states the shipped reason harvest sits *before* PUB in the first place: "Runs last so PR captures complete feature branch, including harvested LEARNINGS." §10.2 never says what an operator observes for the bytes it writes and deletes after the PR exists. Two observably different outcomes are both consistent with the text as written: the delete + LEARNINGS append are pushed (moving the branch head after CI went green, so Phase MERGE evaluates a head no check ran on), or they are not (so `ADVISORY-{feature}.md` is in the merged PR and its content never reaches `LEARNINGS`, falsifying H-2). **Resolution:** §10.2 must state, as an observable, whether the post-PUB distil result reaches the PR, and what the operator sees on the report and on the merged branch in each case. | §10.2 H-1/H-2, §15.2 |
| F-02 | High | Local | **"Revert to a byte-identical pre-invocation tree" is not achievable at A5, where the action includes a push.** §9.2 A5-3 defines one A5 attempt as "fix → push → re-poll". §4.1 then runs CHECK (5), VERIFY (6) and RECORD (7) *after* ACT (4), and each has a revert path; BR-5 ("two tree states, never three"), T-03-2, T-08-2 and §5.3 reason 4 all assert the tree returns byte-identical. A pushed commit is not undone by restoring a working tree — undoing it is a further remote-visible act (a revert commit, a reset+force-push, or nothing), each with a *different* observable for the operator and for the PR's check history. The FSPEC never says which. This is the single most likely place the tier leaves the "third state" A4-6 forbids. **Resolution:** define, at A5 specifically, what "revert" means for a pushed commit and what the operator observes on the branch and on the PR afterwards — or move the push after RECORD so the reverted region is local-only. | §4.1 steps 5–7, §9.2 A5-3, §16.2 BR-5, T-08-2 |
| F-03 | High | Local | **The shipped defaults make A5's attempt budget unreachable, and T-07-6 unsatisfiable.** §3.1 ships `seamBudgetMinutes = 10` and `attemptBudget = 3`; §4.3 V-5 ends the invocation on whichever bound is hit first. But one A5 attempt contains a CI re-poll, and the pipeline's own completion cap for a registered-but-incomplete check run is **30 minutes** (`dev:35`, `CI_COMPLETION_TIMEOUT_MS`), with a 30 s poll interval (`dev:34`). A5-3 explicitly contemplates a re-poll running to that cap and says it "consumes an attempt rather than escalating separately" — but V-5 will already have escalated at 10 minutes, inside attempt 1. So at shipped defaults A5 escalates with `budget-exhausted` on essentially every real CI cycle, `attemptBudget` never binds there, and T-07-6 ("exactly that many cycles occurred") cannot pass. **Resolution:** either make `seamBudgetMinutes` a per-seam value with an A5 default above the CI completion cap, or state that A5's wall-clock bound excludes time spent waiting on the rollup — and name which, since the two give different escalation counts. | §3.1, §4.3 V-5, §9.2 A5-3, T-07-6 |
| F-04 | High | Local | **Queue-side advisory records (A1, A2) have no harvest path, so H-2 is false for them.** §10.1 R-4 requires a record for every invocation including those that took no action, and A1's *only* possible outcomes are `run-candidate` / `hold` / `escalate` with A1-4 fixing "A1 adjudication changes no file". §10.2 H-1 then binds distil-and-delete to Phase PUB — a phase in the **dev** pipeline. For a candidate adjudicated `hold` or `escalate`, and for A2's apply-then-defer-to-the-next-invocation path (A2-4), no `orchestrate-dev` run happens, so no Phase PUB ever runs for that feature and `docs/{feature}/ADVISORY-{feature}.md` accumulates permanently. H-2's "at the end of a completed run, `ADVISORY-{feature}.md` is absent" is therefore only true of the dev-side seams. T-08-3 as written would pass on a dev-side fixture and mask this. **Resolution:** §10.2 must state when a queue-side record is harvested (or that it deliberately persists until the feature's own run reaches PUB), and §10.6 needs a queue-side case. | §10.1 R-4, §10.2 H-1/H-2, §6.3 A1-4, §6.4 A2-4 |
| F-05 | High | Local | **§17.2 removes the advisory summary from exactly the runs that need it, contradicting S-1 and REQ AC-9.4.** §17.2 row 3 says a run that halts at A3 or A4 produces no summary "because the run did not complete". The halt path does build a final report — `dev:8390-8396` returns `buildFinalReport({ … haltReason, haltPhase, … notices })` — so a report exists and the operator reads it. §10.3 S-1 and REQ AC-9.4 both state the report carries the summary unconditionally, and §12.2 uses the summary's *presence* as the sole distinguisher between "enabled but unexercised" and "disabled". Dropping it on halted runs both breaks that distinguisher and removes the audit surface on the tier's primary escalation path. **Resolution:** state that a halted run's report carries the summary for the seams reached so far, and add a halted-run case to §10.6. | §17.2, §10.3 S-1, §12.2 |
| F-06 | High | Local | **Rung resolution is specified twice with observably different results: lazily in §3.2/§3.3, eagerly in §15.2.** §3.2 evaluates the ladder "at the first advisory dispatch of a run"; §3.3 row 2 then says that with the tier enabled and no seam firing "no dispatch happens, so no resolution happens" and the summary names the rung *not exercised*; T-01-4 phrases the unresolvable case as "**When** a seam fires · **Then** the run fails". §15.2 places "resolve the advisory rung ONCE" in the run's prologue, immediately after the config read and *before* the pipeline proceeds, with "neither rung resolves ──► the run fails loudly". Under §15.2 an enabled tier with an unresolvable rung fails a run in which no seam would ever have fired; under §3.2/§3.3 that run completes with five zero rows (§12.2 row 2, T-10-5). §1 asserts §15 "adds no behaviour", so this is not a licensed elaboration. **Resolution:** pick one and make §15.2 cite it. Note that eager resolution also requires a probe dispatch with no seam behind it — a real cost and a real agent turn — which §3.2 should then declare. | §3.2, §3.3, §15.2, §12.2, T-01-4, T-10-5 |
| F-11 | Medium | Local | **T-08-4 depends on a delete mechanism the FSPEC never names, and on a guard message that names the wrong artifacts.** H-3 extends the harvest-before-delete protection to `ADVISORY-*`. That guard is a **PreToolUse:Bash** hook: `guard-harvest-before-delete.sh:35` returns 0 unless the command string contains `CROSS-REVIEW` or `CODE_REVIEW`, and `:37` unless it is an `rm`/`unlink`/`git rm`. It therefore only fires when the delete goes through a Bash command — a delete performed through the workflow's own file seam bypasses it entirely, and H-2's delete is specified as a pipeline step, not as an agent's Bash call. Separately, the refusal text at `:56-60` names only CROSS-REVIEW and CODE_REVIEW, so "refused with the guard's refusal message" (H-3, T-08-4) is under-determined once ADVISORY files are in scope. **Resolution:** state as an observable that the record's delete is subject to the guard (which implies it goes through the guarded channel), and that the refusal message names the artifact class it refused. | §10.2 H-3, T-08-4 |
| F-12 | Medium | Local | **§4.1 orders RECORD last, but R-2 calls the record "a precondition of acting".** In §4.1 the record is written at step 7, after ACT (4), CHECK (5) and VERIFY (6). §10.1 R-2 says "The record is a precondition of acting, not a by-product of having acted", while its own first clause describes the revert path ("the action is not taken — **or is reverted**"). As written the record is a precondition of *keeping* an action, not of taking one. The distinction is not cosmetic: it decides whether an implementer writes the record before touching the tree (cheap to satisfy, and it makes F-02's A5 push tractable) or after (requiring the revert F-02 shows is not well-defined at A5). **Resolution:** either reword R-2 to "a precondition of an action surviving", or move RECORD ahead of ACT in §4.1 — but say which, since they differ in what the record contains when a run is interrupted (§4.4 last row). | §4.1, §10.1 R-2 |
| F-13 | Medium | Local | **§6.2 makes T-04-3's precondition unreachable, and §5.4's A1 gate row is vacuous.** §6.2's flow routes a pre-check-`blocked` candidate to "skip candidate; **NO advisory invocation**". T-04-3 then posits "**Given** the dependency pre-check reports a candidate blocked · **When** an A1 verdict of `run-candidate` is returned for it" — a state §6.2 says cannot arise, so the test as written can only be built by bypassing the specified flow. Relatedly, §5.4 names the pre-check as the gate that "re-runs" for A1, but A1-4 fixes that A1 changes no file, so a re-run of a pure function of unchanged inputs (`precheckDependencies`, `queue:630-649`) necessarily returns what it returned before the agent ran. **Resolution:** state whether A1's gate re-run is a genuine re-evaluation or a defence-in-depth re-assertion of an already-known result, and re-phrase T-04-3 as a defence-in-depth assertion (an agent that returns `run-candidate` anyway is refused) rather than as a reachable flow state. See also the REQ erratum raised for AC-4.5's A1 row. | §6.2, §5.4, §6.3 A1-2/A1-4, T-04-3 |
| F-14 | Medium | Local | **Phase PUB's registered-but-never-completing halt has no specified A5 behaviour.** B-7 records three distinct PUB outcomes that are not a pass: `failed`, the completion-cap halt, and (separately) the no-checks pass. §9.1 fires the seam only "when the check rollup reports a failure", and §9.2 A5-6 explicitly handles the no-checks path — but the completion-cap halt is addressed only by A5-3, which speaks about a **re-poll** *inside* an invocation. The initial case — checks register on the first poll and never complete, so PUB halts with no failing check to diagnose — falls through: no seam fires, no escalation entry, and unlike the no-checks case it is not named in the summary either. §9.3's row conflates it with the re-poll case. **Resolution:** state explicitly whether A5 fires on the completion-cap halt, and if not, name that outcome in the summary the way A5-6 names no-checks. | §9.1, §9.2 A5-3/A5-6, §9.3, B-7 |
| F-15 | Low | Local | **X-d is undecidable at the queue seams.** §5.2 X-d defines declared scope as "the files the PLAN names, plus the files the branch had already touched…". At A1/A2 the candidate has not been picked, so it has neither a PLAN nor a feature branch. A2-5 already constrains A2 to the single REQ file, so nothing unsafe follows — but X-d is stated as a universal exclusion and an implementer will look for the inputs it names. **Resolution:** one clause noting X-d applies to the dev-side seams and that A2's scope is fixed by A2-5. | §5.2 X-d, §6.4 A2-5 |
| F-16 | Low | Local | **E-1's decidable rule decides the re-run, not the flakiness.** §5.2 E-1 permits "re-run a check that failed flakily", but its rule — "the check failed and the re-run is on the identical commit sha, with no push in between" — is a property of *any* re-run and is satisfied by a deterministically broken check. So E-1 permits re-running a hard failure up to `attemptBudget` before escalating. The outcome is safe (it ends in an escalation) but the cost is real: with F-03 unresolved it is also the fastest way to burn the seam budget. **Resolution:** either add an evidence condition (e.g. the same check passed on an earlier run of the identical sha) or say plainly that E-1 does not attempt to decide flakiness and is bounded by budget alone. | §5.2 E-1 |
| F-17 | Low | Local | **A5's default-branch comparison is evaluated ahead of E-1, which makes E-1's reachability depend on a flaky signal.** §9.1's flow and A5-1 put the default-branch comparison first, unconditionally. For a genuinely flaky check, its status at the default-branch tip is itself flaky — so the same failure will sometimes escalate as "pre-existing" and sometimes proceed to E-1, from identical branch state. The behaviour is safe in both directions, but it is non-deterministic and no test in §9.4 pins which way it should go. **Resolution:** one sentence saying the comparison is authoritative even when its input is noisy, and that a flaky-on-default check is deliberately escalated. | §9.1, §9.2 A5-1 |

## Questions

| ID | Question |
|----|---------|
| Q-01 | §3.2's ladder needs a *dispatch* to discover that a rung does not resolve. If resolution is eager (F-06), what does that probe dispatch ask the model to do, and is its cost accepted on every enabled run? If it is lazy, the first real seam pays a wasted dispatch inside its own `seamBudgetMinutes` — is that intended? |
| Q-02 | At A1/A2 the advisory record is written into `docs/{feature}/`. For a candidate whose pipeline has never run, is that directory guaranteed to exist? The REQ lives there, so probably — but §10.5 row 2 ("feature directory does not exist → the write fails, R-2 governs") means the answer decides whether an A1 adjudication can escalate at all in a repo where the REQ is stored elsewhere. |
| Q-03 | §12.1 D-6 says "no file this feature introduces is created merely by running with the tier off". Does that include `docs/_queue/ESCALATIONS.md`? §11.3's last row has the escalation path *create* `docs/_queue/` when absent, so with the tier on in a repo with no queue the tier introduces a directory. Worth stating that this is intended. |
| Q-04 | §9.2 A5-4 says a resolution at A5 means "the rollup subsequently reported green". A re-poll after a push races the old run's rollup — does the FSPEC intend the rollup read to be pinned to the new head sha? If not, a green from the *pre-fix* run can be observed as a resolution, which is exactly the "declare CI passed" outcome P-3 forbids. |
| Q-05 | §7.2 A3-7 gives a class precedence and §7.1's flow branches on `real-defect` first — but §7.3 row 2 says an unclassified finding is malformed and "on budget exhaustion the pipeline halts as today". Is that halt an *escalation* (with an `ESCALATIONS.md` entry and a `budget-exhausted` reason) or a bare halt? §4.3 V-8 says the former; §7.3's wording reads like the latter. |
| Q-06 | Is the advisory tier expected to work in a Claude-created worktree? Per this repo's CLAUDE.md the per-worktree consumer state problem is deferred to D-DIST-07, and A4's rebase and A5's push both act on a branch. If the tier is main-worktree-only, that belongs in §1's "not specified here" or in §13. |
