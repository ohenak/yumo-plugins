| F-01 | High | Local | **The test-pyramid budget is off by ~90 properties, and the Integration share by more than 2×.** §1 states "78 of the properties below are Unit, 21 Integration"; §12.3 repeats "78 Unit properties, 21 Integration, 0 E2E — inside the pyramid budget". The document actually defines **189 distinct `PROP-*` ids**; of the 187 that carry a Level cell the tally is **134 Unit, 39 Integration, 7 Unit + Integration** (counted mechanically over the tables). So ~46 properties need an Integration harness, not 21 — against the **three** harnesses PLAN §6.2 provides, and against O-2's own §13.3 note that the real-tree properties are the suite's slowest. This is a cost claim, not a typo: an implementer sizing A-10/A-11/A-12 from §1 will under-provision by a factor of two. Recompute both totals from the tables and re-state the budget, or re-level the properties to meet it. | §1 "Test-pyramid budget", §12.3 "Level totals" |
| F-02 | High | Local | **PROP-CFG-05's oracle is falsified by shipped behaviour, not by a defect.** The property asserts `readAdvisoryConfigSafely` is called "exactly once per run … asserted by an `_readFile` call-count spy scoped to `ADVISORY_CONFIG_PATH`", and §4.1 correctly notes `ADVISORY_CONFIG_PATH` is `.claude/pdlc.config.json`. That path is **already read twice more** on a full run: `readMergeConfigSafely(readFileFn, MERGE_CONFIG_PATH)` in the Phase I wiring (`pdlc/workflows/orchestrate-dev.js:8040`, constant at `:43`) and `phaseMerge`'s `_configPath = MERGE_CONFIG_PATH` default (`:1373`). A spy scoped to the **path** can therefore never read 1 on a correct build. Scope the count to the advisory reader (spy `readAdvisoryConfigSafely` itself, or a `_readAdvisoryConfig` seam), and say so in the property. | §4.1 PROP-CFG-05 |
| F-03 | High | Local | **PROP-DIS-06 contradicts PROP-DIS-05 + PROP-SUM-06, and its grep scope is undefined.** PROP-DIS-06 pins "**exactly three** `advisory.enabled` sites: the driver's early return, the config-notice emit gate, and the distil-step guard. A fourth site is a defect." But PROP-SUM-06 requires `buildFinalReport` (`orchestrate-dev.js:8595`) to receive `advisory: null` when disabled, while PROP-DIS-05 requires an **enabled**-but-quiet run to carry five zero rows. Distinguishing those two states at the report site is a fourth read of `enabled` — none of the three enumerated sites can make that decision. Separately, the qualifier "on the dispatch path" does not narrow the grep: sites (2) and (3) are not on the dispatch path either, so the property has no decidable scope. Either name the fourth site (and make it four), or name the mechanism by which the report field is derived without re-reading `enabled` (e.g. an advisory `_state` that is `null` when the driver never armed). Both properties are homed in `advisoryDisabled.test.js`, so the conflict lands in one file. | §10.1 PROP-DIS-05/-06, §9.3 PROP-SUM-06 |
| F-04 | High | Cross-Feature | **PROP-REG-08 clause (b) is vacuous by construction under a promoted decision.** Clause (b) is "the direct behavioural observation that **every block of every advisory path** reports `pending === 0`", homed in `advisoryDisabled.test.js`. `docs/_decisions/DECISIONS-test-oracle-mechanics.md` **DEC-ORACLE-01** ("A run-wide assertion cannot live at module level") settles exactly this: jest gives every test *file* its own module registry and may fork workers, so a whole-run observation made from inside one test file "can only ever hold that file's own contributions … trivially true forever — vacuous by construction, not by oversight", and it names the `pdlc-workflow-distribution` skip comparator as the precedent that shipped this way. A whole-run pending count belongs in `globalTeardown` or a custom reporter, and (per the same decision) that transport itself needs falsification. Clause (a) — the source-text scan — is sound and unaffected. Re-home clause (b) or drop it and strengthen (a). | §10.3 PROP-REG-08 |
