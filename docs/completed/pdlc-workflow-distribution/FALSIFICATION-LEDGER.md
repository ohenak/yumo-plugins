## Format (PLAN §3.1)

A property is marked **green** in this ledger only when a **falsification run** has been recorded
for it: the ordered triple *(mutation, red, revert)*.

1. **Mutation, named before the run.** Before running anything, the implementer writes the
   mutation as a one-line diff description against the *subject* — C1 (`pdlc-drift.sh`), C2/C3
   (`check-workflow-drift.sh` / `sync-workflows.sh`), or `orchestrate-queue.js`. Where PROPERTIES
   §7 or §8.1 already names the mutation for a property, the ledger cites that section instead of
   re-describing it. Naming the mutation before running anything is what stops a post-hoc
   rationalisation of a green.
2. **Red observed.** After applying the mutation, record the failing case count and the first
   failure message verbatim.
3. **Revert verified green.** After reverting, record that the suite is green again, and that
   `git diff --exit-code` over the subject file is clean (no subject file is left mutated when the
   batch closes).

A property with **no nameable mutation** is not marked green. It is filed in the **Residuals**
table below instead, with the reason, and counts against §9's property total as unverified — a
property no mutation can falsify is vacuous, and this ledger exists to catch exactly that.

## Residuals

- **PROP-DET-03 — Environment-order independence.** No nameable, effective falsification mutation exists against the subjects (C1/C2/C3). Every real production entrypoint is invoked by the test harness as `runScript` → `spawnFn("bash", [script, ...argv], spawnOpts)` (`driftHarness.js`) — i.e. always `bash <script>`, never a raw `execve` of the script file itself. Empirically confirmed via a standalone experiment chain (`env -i ... A=1 B=1 C=1 bash -c 'python3 -c "...os.environ..."'` vs the same with keys inserted in reverse order): bash's own process, when it starts and imports its inherited `environ` into its internal shell-variable table, destroys/reorders the original insertion order — this happens at bash's own startup, before any script code in C1/C2/C3 runs, and before any child process is exec'd from within that bash instance. By contrast, a single-execve hop (`node -e spawnSync("env", [], {env})` or `env -i ... python3 -c '...os.environ...'`, i.e. no intermediate `bash -c` hop) *does* preserve insertion order end-to-end. Consequence: by the time any C1/C2/C3 code runs, the environment's insertion-order information has already been erased by bash's own startup import, so no mutation added to that code (e.g. a variable-order-sensitive dump or comparison) can ever be made order-sensitive — the order information genuinely no longer exists at that point. The property is therefore true by construction/upstream enforcement (bash's own environment-import behavior), not by any property of C1/C2/C3's logic, and is not falsifiable via subject mutation. The test itself (`"PROP-DET-03 — production behavior is independent of environment-variable insertion order"` in `driftOrdering.test.js`) is left in place and passing, since it still correctly asserts the true (structurally-guaranteed) invariant — it is just not a green ledger entry with a mutation/red/revert triple.
