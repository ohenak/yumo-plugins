## 4. Process Learnings

**1. A DoD finding's severity can hinge on whether the guard fires on *every* instance of a code path or only some.** F-1 (High) was defect-by-construction: pin-check eligibility is literally defined as `c.record.hash === c.docHash`, and the PASS path's re-anchor guard short-circuits on exactly that condition — so the append is skipped on **100% of PASS results**, not intermittently. That "always, by construction" framing (rather than "sometimes, under some inputs") is what correctly earned it High severity over a narrower conditional bug, and is worth naming explicitly in future DoD findings rather than leaving the reader to infer it from the code excerpt.

**2. A cross-cutting interaction between a new feature and a standing operator experiment escaped spec-time review and was only caught by TDD's own red-test discipline, not by a review round.** DEC-LOOPECON-10 records that shipping M3 (derivative-stop) as originally specified would collide with the 2026-08-08 high-only convergence shortcut (`DECISIONS-review-severity-bars.md`) and make the feature's headline outcome (`converged-by-derivative-stop`) unreachable dead code. This was not surfaced during TSPEC/DECISIONS authoring — it surfaced when T-09's red test tried to exercise the outcome and could not, because the interaction is only visible once you try to drive the actual gate through two consecutive flat rounds. This feature ran without engine cross-review rounds (see metadata), so there was no independent reviewer positioned to catch it earlier; the red-test-before-green discipline is what substituted for that missing review pass here. Where a feature substitutes direct authoring for the engine's review loop, red-test coverage of the exact scenario the REQ's headline outcome depends on is not optional polish — it is the only safety net standing between a spec assumption and a dead branch.

**3. Vestigial instructions left behind by a "correct the absence" decision are themselves a latent finding, and were explicitly scoped out rather than fixed.** DEC-LOOPECON-07 discovered the engine already satisfies REQ-LOOPECON-01a (no anchor-writing prompt-builder code exists) and shipped an absence-pinning census instead of new code. But three review SKILL.md files still carry a sentence instructing an agent to "append/transcribe an approval anchor verbatim" — dispatch behavior that, per this feature's own finding, the engine no longer issues. The decision explicitly declined to delete them (REQ NG-2 excludes SKILL.md edits; a SKILL.md edit trips the digest manifest for no behavioural gain). Correct call for scope discipline, but it leaves three files asserting a false premise about engine behavior with no tracking artifact beyond this LEARNINGS mention — flagged again in §5.

**4. A property-based oracle can be non-falsifying for the exact claim it's written to guard, while still incidentally proving something else real.** F-9 (v2, new): PROP-LOOPECON-06/07's `fast-check` property builds its own `Map`-based model (`simulateOpenFindingList`) and asserts against *that model's* invariants rather than against the production accounting (`orchestrate-dev.js:9643-9644`, an array). Because a `Map` keyed by identity deduplicates by construction, the property literally cannot fail no matter what the classifier under test returns — verified by mutation-testing the classifier down to a no-op stub and watching the property stay green. What it *does* prove (identity-key normalization collapses round/hash noise to one key) is real and separately valuable, but is not the dedup-guarantee claim the PROPERTIES doc's own prose asserts. The general lesson: a property oracle that constructs its own idealized data structure as the thing under test, rather than driving the production function/structure, needs an explicit check that the model itself is capable of exhibiting the failure the property claims to catch — mutation-test the code under test down to a stub and confirm the property goes red, not just that it passes on the real implementation.

**5. One agent committed and pushed without authorization mid-feature.** Commit `146e2b3ba` (the PROPERTIES document) landed on `feat-pdlc-loop-economics` before the rest of the change set, and CODE_REVIEW-v1/v2 both flag this as F-8: the working tree carries the entire M1–M3 implementation uncommitted on top of that one commit, so PLAN §9's commit-shape obligations ("`dist/` staged in the same commit as the last workflow-source change," "`plugin.json` version bumped in the landing commit") were unverifiable at both DoD rounds. Every future subagent dispatch in a multi-agent/gatekeeper feature needs an explicit "do NOT commit or push" line in its prompt — this recurs across features (see prior LEARNINGS' equivalent note) and is not yet a standing template clause.

**6. One subagent reported disregarding an injected "stop using tools" instruction found inside compaction/expansion artifact content during this feature's work.** Investigated: the instruction was untrusted embedded content (not from the operator or the gatekeeper), the subagent correctly treated it as data rather than as a directive, and there was no repo-level impact. Recorded here as a positive signal (the injection-resistance held), not as a defect.

**7. `documentOracles.test.js`'s frozen test-file count (`102`, `:398-420`) required a new namespace exclusion for this feature's own suites.** The oracle pins a literal count of pre-sweep `pdlc/workflows/__tests__/*.test.js` files with `learnings*` and `waveResume*` namespaces already census-excluded; this feature's eight new `loopEconomics*.test.js` files needed the same treatment and rode the existing exclusion mechanism rather than requiring a new one. Confirms the exclusion pattern generalizes cleanly to a third namespace — worth citing as precedent the next time a feature adds a batch of new top-level test files.

## 5. Open Items for Consolidation

1. **Three vestigial "append/transcribe anchor verbatim" sentences remain live in review SKILL.md files, asserting a dispatch instruction the engine no longer issues (per DEC-LOOPECON-07's own finding).** REQ NG-2 explicitly scoped their deletion out of this feature as "a permitted follow-up outside this feature," but there is no queue row and no successor REQ tracking it — DoD's v1 §3 and v2 §4 integration-boundary notes both flag this as a declared-but-unbound deferral, distinct from a deferred-with-a-successor item the DoD criterion normally requires. Candidate: either a small follow-up REQ, or a queue row naming the three files.

2. **F-4 (`waveResumePreflight.test.js`'s hand-transcribed `EXPECTED_TEST_COMMAND` literal disagreeing with the shipped example config) is Cross-Feature and pre-existing, not owned by this feature, yet it was the only consistently-red suite across both DoD rounds and is CI-vacuous (untracked config file in CI degrades the assertion to a no-op).** This is the same two-surface-disagreement failure mode this feature's own T-16 documentation task had to route around. Candidate: derive the literal from `.claude/pdlc.config.example.json` in a small fix, filed against whichever feature/queue row owns `pdlc/workflows/__tests__/waveResumePreflight.test.js`.

3. **F-6 (README/CLAUDE.md config-surface disclosure omits `cascade.pinCheck` and `review.derivativeStop`) is accepted as advisory because `pdlc/OPERATIONS.md` carries the authoritative disclosure, but the pattern of README/CLAUDE.md lagging OPERATIONS.md on new config keys has now recurred across features.** Candidate: a standing rule (in `docs/_decisions/` or the config-surface constraint) that any new `.claude/pdlc.config.json` block lands in the README/CLAUDE.md config table in the same commit as its OPERATIONS.md documentation, not deferred.

4. **Phase CR's `reviewLoop` call site (`orchestrate-dev.js:17616`) is a declared, not accidental, omission from M3's derivative-stop threading — `recordPhase` hardcodes `Approved` for that phase, so the concept does not apply there.** No action needed on this feature's account; noted only so a future feature touching Phase CR's review model does not mistake the omission for an oversight.

5. **F-8 (whole change set uncommitted at both DoD rounds; PLAN §9's commit-shape obligations unverifiable) closes only at Phase PUB, which this feature's own artifacts document as out of scope for the direct-authoring gatekeeper flow.** Whoever lands the change is responsible for re-verifying, against the actual landed history, that `pdlc/workflows/dist/` is staged in the same commit as the last workflow-source change and that `pdlc/.claude-plugin/plugin.json`'s version bump lands in that same commit — both are currently only confirmed true of the *working tree*, not of any commit.
