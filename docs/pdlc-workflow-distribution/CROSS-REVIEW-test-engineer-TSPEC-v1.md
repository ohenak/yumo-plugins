| F-01 | High | Local | **§4.3 conjunct (a) is set equality, not bag equality — it cannot catch double-classification, which is the failure it is justified against.** The text argues (a) is stated "over the **row-id set**, not over a count" because "a count assertion passes against an implementation that classifies one row twice and another zero times". True — but the set assertion is not strictly stronger. `new Set(C.map(r => r.rowId)) equals new Set(expectedRowIds)` passes against an implementation that emits an as-found `classify` record **twice for every row**, which a count assertion would catch. That is not a hypothetical: FSPEC §10 O-1 names "double-count on a conforming run" as the exact hazard the phase labels exist to prevent, and §4.3's own `assertPostCopyNarrow` note says an over-broad re-classification makes NFR-2's bound "quietly become `2 × 3 × \|rows\|`". The `seq` self-check does not help (it asserts monotonicity, which a double-classifier satisfies). The oracle needs **multiset equality** — "each id in `expectedRowIds` appears in `C` exactly once, and no other id appears" — and `assertPostCopyNarrow`'s set equality needs the same correction. | §4.3 (a); §4.3's `assertPostCopyNarrow` |
| F-02 | High | Local | **The trace grammar declares a `phase` field for every record but assigns a phase value to only one op, so `assertPhaseOrder` is unimplementable and §1.4's phase floor is unassertable.** §4.1 fixes `phase ::= "as-found" \| "post-copy" \| "post-run" \| "run"` on **every** record, and §2.2 makes `pdlc_classify_row` the "only place the trace's phase label is set". §4.2's op table then gives `rowId` and `arg` for all twelve ops and a phase for none. What phase does `mkdir` carry? `write`? `copy`? `backup`? `delete`? `manifest-read`? §4.3's `assertPhaseOrder` drops only `run` records and requires the remainder be "a prefix of `[as-found, post-copy, post-run]`" — against an implementation that stamps `mkdir`/`copy` with, say, `as-found`, that predicate is violated on a *conforming* run; against one that stamps them `run`, they are silently dropped and the assertion is vacuous over the mutating ops. §1.4's floor ("all three labels observed on one sync run") likewise cannot be evaluated without knowing which records are eligible to carry which label. I cannot write `assertPhaseOrder` from this document. Pin a phase per op in §4.2's table (or state that non-`classify` records carry `run` and correct `assertPhaseOrder` accordingly). | §4.1, §4.2, §4.3, §1.4 |

On root, two members are unreachable, the meta-oracle fails, and the suite is red for a reason unrelated to the code. | F-04 | Medium | Local | **§12.1's D-clause table under-covers D1–D8, violates its own one-mutation rule, and does not discharge O-19(b) as §16 claims.** (a) FSPEC O-19(b) enumerates six mangled-relay shapes — fenced, **re-wrapped**, truncated, key-dropped, **array-replaced-by-scalar**, state-value-reworded. The table has fenced, truncated, key-dropped and reworded; there is **no** re-wrapped fixture (e.g. `{"result": {...}}`) and **no** array-replaced-by-scalar fixture (e.g. `rows: "[]"`), yet §16 states "(b) is **discharged in design** by §12.1's table". ## Questions

| ID | Question |
|----|---------|
| Q-01 | §3.2.1 makes a tool absent by omitting it from a single-directory `PATH`. C1 is bash and several probes (`printf`, `[`, `read`) are shell builtins, but `command -v python3` inside the subject will also consult builtins/functions before `PATH`. Does `makeToolDir` also clear `BASH_ENV`, and does the sandbox guarantee the child is not a login shell that sources a profile which re-exports `PATH`? §3.2's `sandboxEnv` sets `PATH` but the invocation is `spawnSync("bash", [scriptPath], …)` — non-interactive, non-login, so no profile — worth stating, since the whole `json-tool-absent` fixture family rests on it. |
| Q-02 | §4.2 allocates "a fresh trace path per invocation (`<tmp>/trace/<n>.tsv`)" and `parseTrace()` asserts exactly one `run` record. Jest runs test files in parallel workers by default. Is `<n>` per-worker-unique, and does `runScript` create `<tmp>/trace/` per consumer tree (§3.3 returns a per-tree `tmp`) or per suite? If per suite, two workers can collide and `parseTrace`'s single-`run` assertion becomes a flake rather than a detector. |
| Q-03 | §11.2's driver sources C1 and reads `format TAB id TAB stamp TAB nn` from stdin. §4.1 establishes that tab is excluded from M6's id charset — but is it excluded because M6 says so, or because §4.1 asserted it? If `M6_ID_REGEX` (§11.3 row 1) is the authority and it permits tab, both the trace grammar and the batched driver lose their delimiter. Which document pins M6's charset? |
| Q-04 | §10.1's tracked-ness guard uses `git ls-files --error-unmatch`. On a `describeOrSkip("git")`-skipped runner, does the guard skip too — and if so, is the "the fixture is not committed" failure mode (the whole reason the guard exists) simply unavailable there, or does the file-count check stand alone? |

## Positive Observations

- **§14's AT mapping is complete and I verified it mechanically.** FSPEC §12 and TSPEC §14 enumerate exactly the same 39 ids (AT-1…AT-36 with AT-8a/8b, AT-14b, AT-18a/18b, and no AT-8 or AT-18 stragglers) — no omissions, no inventions. Every row names a file, a case description and its §13 fixtures. This is the strongest part of the document.
- **§1.2's harness decision is argued from the right property, not from convenience.** "The oracle must stay strictly outside the subject's dependency set" is the correct reason to reject bats, and it is load-bearing for AT-14 specifically. §3.4 rule 1 (`JSON.parse`, never a subprocess) enforces it at the read-back layer rather than leaving it as an intention.
- **§3.4 rule 2 is exactly right and is the kind of thing usually missed:** `readDriftState` returning `null` only for absent and **throwing** on unparseable. A helper conflating the two would false-green rung (iii)'s "no record" assertion against an implementation that wrote a corrupt one.
- **§5.2's decision that tokens 10 and 12 truncate real bytes rather than faking the comparison** is the correct construction, and the justification (an implementation that skips the re-read must genuinely land a truncated file) is precisely the red-direction reasoning FSPEC AT-27/AT-35 demand. R-9's ≥64-byte fixture bound closes the degenerate case.
- **§4.4's use of `ENOTDIR` rather than a permission bit** for the blocked-trace fixture, with the stated reason ("the one test that guards the whole trace-based oracle set" must not be the most-skipped one), is a genuinely good piece of test engineering.
- **§6.1 note 1 on `backup-verify` is correct and well argued.** It has no permission form — the failure is a filesystem lie, not an access decision — and that single cell is the honest justification for the fault seam existing at all.
- **§2.4's `mapDriftState` returning the row number** is the right affordance, and §12.2's requirement that each of the ten fixtures defeat every higher row is the correct precedence-chain discipline (it is also the check my own review checklist calls "precedence-chain false-green").
- **§3.3's `setRowState` re-deriving the expected classification and throwing on mismatch** — the fixture builder as its own first oracle — closes the two traps (`stale` with plugin-equal bytes, `local-edit` with no entry) that this ladder invites.
- **§10.1's exemption-(iv) legality argument is sound**, including the observation that (iv) does not fire when the oracle runs over the fixture root, and the anchored-gitignore landing constraint (§16) correctly identifies a hazard that would have turned AT-23 from `== 7` into `== 0` with no diff to explain it.
- **§8.2's `gitTreeBrokenProbe` is a genuine falsifier** of the never-fall-through rule: a git tree whose `.claude/` *would* satisfy the walk, with only the git guard faulted. That is the right fixture, and it is only constructible because O-3's one-token-per-guard split was honoured.
- **§11.2's batched driver (one spawn per property run)** is correctly framed as a requirement rather than an optimisation, given §1.1's no-CI premise.

## Recommendation

**Needs revision**

To reach approval:

1. **F-01** — restate §4.3 conjunct (a) (and `assertPostCopyNarrow`) as **multiset** equality: each expected row id appears in the as-found `classify` set exactly once, no other id appears.
2. **F-02** — assign a `phase` value to every op in §4.2's table, and restate `assertPhaseOrder` and §1.4's phase floor over that assignment.
3. **F-03** — either add fault tokens for the P1–P4 artifact-read guards and re-close §5.2, or make §1.4's row-reason floor capability-aware; either way extend §1.3's named inventory and R-2 beyond "two holes", and fix §7.1's P1 F-twin cell (`manifest-read` yields the baseline reason `plugin-root-unreadable`, not the row reason `plugin-artifact-unreadable`).
4. **F-04** — add re-wrapped and array-replaced-by-scalar rows, cover all three D6 arrays and D4's `baselineStatus`, and split the two-mutation D7/D8 rows.
5. **F-05** — enumerate which tokens are selector-bearing, give the backup-id selector a query form (or drop it), and pin the behavior of a selector on a non-scoped token.
6. **F-06** — correct or remove the two unreachable permission cells in §6.1.
7. **F-07** — put `pdlc_backup_format` and `pdlc_backup_parse` in §2.2's surface table and reconcile `pdlc_prune_backups`' two signatures to one.
8. **F-08** — give `manifest-malformed` and `plugin-root-unset` construction recipes in §13.
9. **F-09** — split AT-34 and AT-31 into per-fixture `it()` blocks.

F-10 through F-13 are Low and may be folded into the same revision.
