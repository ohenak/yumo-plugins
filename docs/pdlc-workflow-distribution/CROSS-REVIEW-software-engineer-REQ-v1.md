## Findings

| F-01 | High | Cross-Feature | **The REQ names the wrong distribution unit.** Every AC hashes `pdlc/workflows/{name}.js` against `.claude/workflows/{name}.js`. In the current working tree the artifact the runtime actually loads is `.claude/workflows/{name}.bundle.js`, generated by `pdlc/workflows/build-runtime.mjs`; the ES module is no longer loadable at all (`pdlc/workflows/orchestrate-dev.js:15` — `import * as fs from "fs"`, and the runtime has no `import`/`fs`). Under that model AC-1.3 ("byte-identical → `in-sync`") is unsatisfiable for the executing artifact, because the bundle is a transform (IIFE wrap, exports stripped, `runtime-adapter.js` inlined) — measured here: `pdlc/workflows/orchestrate-dev.js` = `2cfc66c1f3…`, `.claude/workflows/orchestrate-dev.bundle.js` = `ae2e586f3d…`. The REQ must name the distribution unit explicitly, and if it is the bundle, define comparison as source→generated-artifact (hash the *build inputs*, or ship + hash the bundle), not byte equality of two different files. | §1, AC-1.1, AC-1.3, AC-3.1 |
| F-02 | High | Local | **The installed plugin package contains no bundle, so AC-3.1's copy source does not exist for the executable artifact.** `~/.claude/plugins/cache/yumo-plugins/pdlc/0.10.0/workflows/` holds `orchestrate-dev.js`, `orchestrate-queue.js`, `__tests__/`, `package.json` — and no `*.bundle.js`. In this repo the bundles are untracked (`git status` shows `?? .claude/workflows/orchestrate-dev.bundle.js`, `?? …orchestrate-queue.bundle.js`) and not gitignored, so they are in neither git nor the plugin package. BL-01 asks only whether the plugin path *resolves*; the harder unproven premise is whether the plugin *contains* the file to copy. Prove that before AC-3.1 is written. | BL-01, AC-3.1 |
| F-03 | High | Local | **The distribution chain has three nodes; the REQ models two.** Real chain: repo `pdlc/workflows/*` → **version-pinned installed cache** `~/.claude/plugins/cache/yumo-plugins/pdlc/0.10.0/workflows/*` → consumer `.claude/workflows/*`. The cache is pinned to `plugin.json` `version: 0.10.0` and refreshes only on plugin update. A consumer byte-identical to a stale cache is reported `in-sync` while being behind the merged source — precisely the failure US-04 exists to prevent. No AC compares cache↔repo; AC-5.2 only *reports* the plugin version. Define which node is "the plugin source" (see Q-05) and how staleness of that node itself is detected. | AC-1.1, AC-5.2, US-04 |
| F-04 | High | Local | **AC-4.1 cannot satisfy NFR-1 or NFR-2 in the workflow runtime.** `orchestrate-queue` executes in the restricted runtime with no `fs`, `process`, `import` — all IO reaches it through `runtime-adapter.js`, which re-expresses file reads/existence checks as `agent()` calls. A drift check invoked from `orchestrate-queue` is therefore an LLM turn: non-deterministic (violates NFR-1, "no LLM in the check path") and seconds-to-tens-of-seconds (violates NFR-2, <500 ms). Either specify a concrete non-LLM mechanism (e.g. the SessionStart hook writes a drift state file that the queue reads via one injected read), or scope NFR-1/NFR-2 per surface and accept an agent call in the queue path. | AC-4.1, NFR-1, NFR-2 |
| F-05 | High | Local | **Bootstrap paradox: AC-4.1 puts the detector inside the artifact whose staleness it detects.** A consumer whose `orchestrate-queue` copy predates this feature contains no drift check and reports no drift — zero coverage for the first and worst instance of the problem the REQ exists to solve. The SessionStart hook (REQ-DIST-02) loads from the installed plugin and does not have this property. The REQ must state that the hook is the primary detector and the queue check is defense-in-depth, and must state what happens on first adoption (how does a consumer running the pre-feature script ever learn?). This is the same class of issue `docs/_queue/QUEUE.md` §Bootstrapping already flags for this queue. | AC-4.1, REQ-DIST-02 |
| F-06 | High | Local | **`local-edit` is decided by mtime, which no distribution step preserves.** AC-1.1 defines `local-edit` as "consumer differs and the consumer's copy is newer". `git clone`/`checkout` stamps every file with checkout time; a plugin (re)install restamps the whole cache — observed: every file under the 0.10.0 cache carries the same `27 Jul 17:49`. A fresh consumer clone therefore classifies a genuinely-behind file as `local-edit`, and AC-2.3 then **suppresses the remediation command** — a silent false negative that defeats US-01 and US-03 exactly when the operator is least able to notice. Direction requires provenance (a manifest recording the hash of the last synced version per file), not timestamps. | AC-1.1, AC-2.3, US-03 |
| F-07 | High | Local | **The "managed set" is never enumerated, and `pdlc/workflows/` contains files that must never be copied.** It holds `runtime-adapter.js` (explicitly "inlined, never imported" — copying it to a consumer is wrong), `build-runtime.mjs`, `package.json`, `package-lock.json`, `.gitignore`, `__tests__/`, `node_modules/`. AC-1.1/AC-3.1 say only "`{name}.js`". A glob-based implementation ships non-distributables into `.claude/workflows/`. Require an explicit manifest in the plugin (`plugin source path → consumer path`, one row per managed script) as the sole enumeration authority. | AC-1.1, AC-1.4, AC-3.1 |
| F-08 | High | Local | **No configured threshold or flag is declared with a location, owner or default mechanism.** `distributionCheckEnabled` (AC-4.3) names no file; pdlc has no config file today — comparable flags are in-source constants (`PHASE_H_ENABLED`, `PHASE_DOD_ENABLED`, `MODEL_DEFAULT` in `pdlc/workflows/orchestrate-dev.js`). If this flag lives in the workflow source it ships inside the very artifact that drifts, and an operator toggling it locally makes that file `local-edit`, which under AC-2.3 suppresses the warning. Same gap for NFR-2's 500 ms (no measurement point, no owner, no failure behavior when exceeded) and AC-3.4's backup (no path, naming, or retention). ## Questions

| ID | Question |
|----|---------|
| Q-01 | Which file does a consumer's workflow runtime actually load today — `.claude/workflows/{name}.js` or `.claude/workflows/{name}.bundle.js`? Name the repo and the evidence. Every AC in REQ-DIST-01/03 depends on the answer. |
| Q-02 | Are the generated bundles intended to be committed to `yumo-plugins` and shipped inside the plugin package? They are currently untracked and absent from the 0.10.0 plugin cache. |
| Q-03 | §1's spot-check ("both byte-identical, last synced five days earlier") — which repo, which commit? It is not reproducible from this repo, and F-03 means "identical to the cache" and "identical to the source" are different claims. |
| Q-04 | What filesystem roots does the SessionStart hook have? Specifically: how does it locate the *consumer repo root* when the session starts in a subdirectory, and is `${CLAUDE_PLUGIN_ROOT}` guaranteed set for SessionStart (all three current hooks assume so)? |
| Q-05 | For AC-1.1, is "the plugin source" the version-pinned install cache or the checked-out `yumo-plugins` source tree? A consumer machine generally has only the former. |
| Q-06 | Does anything prevent the plugin cache directory name from changing between versions (`…/pdlc/0.10.0/…`)? If resolution hardcodes a version, every plugin release breaks the check. |

## Positive Observations

- AC-1.5 plus NFR-3 correctly protect repo-local workflows from the sync operation, and the rationale paragraph explains *why* concretely rather than asserting it. This is the single most destructive failure mode of the feature and it is closed by construction.
- AC-1.2's "absence of evidence is not evidence of sync" is the right default for a detector, and AC-2.4's fail-open hook is the right default for a session-start gate. The two are correctly opposite.
- AC-2.3 recognising that `local-edit` needs a *different* remediation from `stale` is a genuine insight — the feature would be actively harmful without it (see F-06 for why the detection it rests on is unsound).
- The deferral table is honest about D-DIST-02 (loading from the plugin path directly), which is the real fix and is correctly scoped out with a stated reason.

## Recommendation

**Needs revision**

Must change before FSPEC:
1. Resolve F-01/F-02 first — name the distribution unit (module vs generated bundle), prove the plugin package contains it, and re-state AC-1.1/1.3/3.1 against that unit. Everything else is downstream of this.
2. Model the three-node chain (F-03) and say which node AC-1.1 compares against.
3. Replace mtime-based direction detection with a recorded-hash manifest (F-06).
4. Resolve AC-4.1 against the runtime sandbox — either a non-LLM mechanism or scoped NFRs (F-04) — and state the first-adoption story (F-05).
5. Add an explicit managed-script manifest (F-07) and declare `distributionCheckEnabled`, the 500 ms budget and the backup policy with file + owner + default (F-08).
