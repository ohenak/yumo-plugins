| F-01 | High | Local | **AC-6.5's new working-tree fixture contains no `.claude/` directory at all, so AC-0.5 resolves it to `repo-root-unresolved` and every one of AC-6.5's three assertions fails — and the AC's two "equivalent" constructions are not equivalent on exactly this point.** The row now reads: build the fixture from "the working tree's tracked, non-ignored files — `git ls-files -z` at `<repoRoot>` copied into a fresh directory under `os.tmpdir()` (**equivalently**, `git clone --local --no-hardlinks` followed by an overlay of those files)". These differ in one decisive respect: the clone form **is a git repository**, the copy form is not. Trace the copy form through AC-0.5. Step 1 requires "`git rev-parse --git-dir` succeeds"; run with the fixture as cwd under `/var/folders/…` it does not (no repository there or above it), so step 1 never applies and step 2 runs: "walk upward from `$PWD` to the nearest ancestor containing `.claude/`, stopping before `$HOME` and before `/`". The fixture has no `.claude/` — AC-6.5 says so itself ("The `.claude/workflows/` directory does not exist in the fixture") and I verified the stronger fact at HEAD: `git ls-files .claude/` returns **only** the four workflow paths, all four of which AC-3.9's landing step `git rm`s, after which **no file under `.claude/` is tracked at all**, so `git ls-files -z` copies no `.claude/` into the fixture. Neither do its `os.tmpdir()` ancestors. Step 2 therefore terminates unresolved ⇒ step 3 ⇒ `baselineStatus: unresolved`, reason `repo-root-unresolved` ⇒ AC-3.1 copies nothing, AC-3.3 row 1 exits **3** (not `0`), AC-4.1 row 3 blocks (not *proceed silently*), and the bundles never appear. The only end-to-end bootstrap oracle in the feature is unreachable again — the same class of defect as my v7 F-02, reintroduced one layer along by the fix for v7 F-03. | F-03 | Medium | Local | **"Readable" is not a well-defined predicate for the thing these ACs use it for, and no fixture mode is specified — so the three permission-derived reasons and the unreadable-parent axis value cannot be built without guessing.** Establishing the *absence* of a named path requires **search (`x`)** permission on the parent (`stat`/`test -e` fail with `EACCES` without it); *listing* a directory requires **read (`r`)**. The two are independent bits and give opposite answers: a parent at mode `0111` (x, no r) is "unreadable" by the ordinary meaning yet absence **can** be established through it; a parent at `0444` (r, no x) is "readable" yet `stat` on any child fails, so absence **cannot** be established. ## Positive Observations

- The AC-2.8 `in-sync` fix is not a wording patch: rescoping "not reachable" to `generatedBy: "sync"` and grounding it in AC-3.9's *post-copy* guard is a claim I could verify mechanically against AC-3.9's own text, and it holds — including the non-obvious case (already-`in-sync` row, nothing copied, guard still passes) that the remediation depends on. That is the second time in this document's history that an "unreachable" claim has been narrowed to precisely what it is true of rather than deleted.
- AC-2.6's per-surface `supersedingState` table with the consequence spelled out — "the same fixture yields different golden output at different surfaces … by construction, not by accident" — is the single most useful paragraph for a test author added in this revision. It converts a defect I would otherwise have discovered while writing a golden test into a planning input.
- AC-1.8(i)'s "The generator must produce `parent-absent` as a first-class value; a suite that only ever creates `.claude/workflows/` before generating is not exercising the bootstrap path AC-6.5 asserts" is the right way to close a generator gap: it names the wrong implementation as well as the right one.
- AC-1.2's four-row reason→condition→remediation table makes the *reason* set falsifiable for the first time — each member now differs from its neighbours in an operator-visible way (which is what my F-04 is asking to complete, not to undo).
- AC-6.5's `realpath` row anticipates the macOS `/var` → `/private/var` hazard and correctly records that AC-0.5 check (c) is itself safe. That is a hazard I checked independently at v7 and the REQ has now internalised it.
