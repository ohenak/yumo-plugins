## Findings

| F-01 | High | Local | **A sync run's row states are unspecified, and the FSPEC contradicts itself on them.** §3 says classification "Runs once per managed row … against the filesystem **as found** — before this run creates anything", and §4.2's five-step ordering is `resolve baseline → classify → build record → mkdir → write drift state` — the copy, backup and retirement steps do not appear in it at all. But §5.7 requires "R's **POST-COPY** state", §5.8 requires the exit code over "the state observed **at the end of the run**", and §4.3/§6.2 rest on "a post-sync drift state is current within the same session, so an operator who syncs mid-session unblocks the queue without restarting". Those cannot all hold: if the record written at §4.2 step 5 carries the pre-copy classification, a successful sync writes `rows[].state: "stale"` and the queue stays `blocked` at §6.2 row 6 — the mid-session unblock claim is false and AC-2.7's stated consequence fails. The FSPEC must state (a) where copy/backup/retire sit in §4.2's ordering, (b) that a sync run records **post-copy** row states, and (c) **how** the post-copy state is obtained — a second classification pass (which contradicts §3's "runs once … as found") or derivation from copy success. §10 O-1's phrasing ("scope the assertion to a **single** classification invocation") implies the author is aware there may be more than one; the document never says so. This is implementation-blocking: two engineers will build two different products from §4.2 and §5.8. | §4.2, §4.3, §5.7, §5.8, §3, §6.2 |
| F-02 | High | Local | **§5.5's copy procedure omits the mandated verified backup for `stale` rows.** The pseudocode is `if state ∈ {stale, missing} → copy` (no backup) / `elif {local-edit, unverified} and --force → verified backup, then copy`. A `stale` row is an **existing consumer file being overwritten**, and AC-3.4 binds "Given a sync overwrites or deletes **any existing file** … the pre-existing content is first written to `.pdlc-backups/…` and verified before the destroying operation". §4.7 ("every destroying operation in §5"), §5.6 ("Every overwrite or delete this feature performs is preceded by a verified backup") and §3.2 ("`missing` is **the one** non-`unknown` state that sync overwrites *without* a backup") all say the opposite of §5.5. As written, §5.5 is the normative procedure an implementer transcribes, and it destroys operator content with no backup on the most common sync path. Fix §5.5's flow to `stale → verified backup, then copy`, and add an acceptance test for it (AT-8 covers only the `--force`/`local-edit` path). | §5.5 vs §3.2, §4.7, §5.6, AC-3.4 |
| F-03 | High | Local | **§3.3's first-match ladder contradicts the row-reason precedence declared immediately below it (and in REQ §4).** The declared precedence is `hash-tool-absent` > `plugin-artifact-missing` > `plugin-artifact-unreadable` > `consumer-artifact-unreadable`, justified explicitly ("`hash-tool-absent` outranks the rest because it is a property of the machine"). The ladder evaluates `P5 unavailable (no hash tool) → hash-tool-absent` **last**, after all three path reasons. On a machine with no hash utility **and** a missing plugin artifact, the ladder emits `plugin-artifact-missing` while the declared precedence demands `hash-tool-absent`. §3.3 claims single-valuedness is "structural rather than asserted" — the structure and the assertion disagree, and PROPERTIES' O-9 obligation ("both declared precedences") cannot be satisfied against this ladder. Either reorder the ladder to put the P5 probe first, or state that the ladder order **is** the precedence and correct the reason-precedence table (which would then deviate from REQ §4 and needs recording as such). | §3.3 |
| F-04 | High | Local | **§6.2's queue mapping is not total, and performs no shape validation of the record.** Row 1 rejects only `absent / unparseable / schemaVersion != 1 / baselineStatus absent`. A record with `baselineStatus: "resolved"` and `rows` absent or `[]` matches **no row 1–9**: rows 3–8 all require a non-empty predicate and row 9 explicitly requires "non-empty rows". The same hole exists for a record with a `rows[].state` value outside the six states, and for `retiredPresent` / `writeFailures` absent rather than `[]`. AC-1.8-class totality is demanded of the shell classifier but never of the mapping the queue actually gates on, and the undefined region falls on the *proceed* side in any naive implementation (`rows.some(...)` over `undefined` throws; over `[]` returns false). The mapping needs an explicit terminal row — "anything else ⇒ `blocked`" — plus a required-key/array-presence check folded into row 1. This is the feature's own failure mode: a green pipeline over a record that verified nothing. | §6.2 |
| F-05 | High | Local | **§4.6 and AT-18 contradict approved AC-2.9(5) without recording a REQ deviation.** AC-2.9(5) states an unrecognised `PDLC_FAULT` token "prints one stderr line, injects nothing, and uses the entrypoint's normal exit — **4 on `--check`/sync**, 0 on the hook". §4.6 instead pins `--check`/sync to "its **computed** exit (0–4)" and argues "an unrecognised token … must not manufacture a 4"; AT-18 then pins the oracle `--check` **exits 0** on an otherwise-green tree. The FSPEC's own OQ-5 shows the correct handling of a REQ divergence (state it, justify it, invite a REQ amendment); O-2 must do the same, or conform to AC-2.9(5) and change AT-18. | F-06 | High | Cross-Feature | **§6.1 discharges BL-04 against the module's signature, not against the runtime that actually executes.** The injected `_readFile` the queue bundle receives is `rtReadFile` in `pdlc/workflows/runtime-adapter.js` — an **`agent()` call pinned to `haiku`** that asks a model to echo the file's contents verbatim (`build-runtime.mjs` `QUEUE_ENTRY` wires `_readFile: rtReadFile`). Consequences the FSPEC does not address: (1) NFR-1's "no judgement in an LLM turn" is not structurally true at the one seam this feature depends on — a model transcribing a JSON record with 40-char sha1s can truncate, re-wrap, fence or "tidy" it; (2) `rtReadFile` returns `null` for absent **and** for every transport failure and non-string result, so §6.1's "whose contract returns `null` for an absent file" is narrower than the seam's real behaviour; (3) the dangerous case is a transcription that still *parses* but has lost a key or an array member — which lands in F-04's undefined region and proceeds. The FSPEC must either specify defensive validation on the parsed record (see F-04) so that any record failing a strict shape check is `blocked`, or state the residual explicitly the way §4.4 rung (iii) is stated. | F-07 | Medium | Local | **§1.4's ordering invariant is false for the same-second collision case the grammar itself defines.** The claim is "The stamp is fixed-width so `LC_ALL=C` lexicographic **descending** sort **is** reverse-chronological". With the optional `-N` suffix, `…091402Z-2.bak` and `…091402Z.bak` compare on byte `-` (0x2D) vs `.` (0x2E): descending order puts the **un-suffixed** (older, first-written) file ahead of `-2` (newer). AC-3.5's P0 oracle — "restoring the **newest** backup for that id yields byte-identical pre-sync content", described in §5.6 as "the one oracle … that cannot be false-greened" — therefore restores the wrong file whenever two backups for one id land in the same second, and §5.6's "newest 5 per id" retention prunes the wrong member. Either always emit `-1` for the first backup in a second, or make the sort key `(stamp desc, N desc with absent N == 0)` explicitly rather than a plain filename sort. | §1.4, §5.6 |

## Positive Observations

- **Every existing-code claim I could check verifies.** §0.3/§7.5 item 4's exit-126 claim is accurate — all three shipped hook scripts are index mode `100644` and non-executable on disk (`git ls-files -s pdlc/hooks/scripts/`), and `hooks.json` invokes them by path. §2.3's Python-discovery-loop reuse claim is accurate (`for cand in python3 python py` in all three scripts). §6.1's `_readFile` null contract is accurate at the module level (`defaultReadFile` in `pdlc/workflows/orchestrate-queue.js` returns `null` on any throw; `readFileFn(queuePath)` distinguishes `null` from `""`). §7.5 item 5's "**7 files today**" is exactly reproducible: applying the five patterns and the four exemptions yields `docs/_queue/QUEUE.md`, `docs/design/MASTER-PLAN-engineering-loop.md`, `docs/PLAN-pdlc-integration-boundary-gates.md`, both orchestrator `SKILL.md`s, and both `pdlc/workflows/orchestrate-*.js` — 7, including the two SKILLs as claimed. This is a materially better citation record than the REQ rounds.
- **§7.5's exemption clause (ii)** — `docs/<X>/` containing `REQ-<X>.md` rather than "any `docs/` subdirectory" — is load-bearing and correct: my reproduction confirms the loose form would drop `docs/_queue/` and `docs/design/` and take the count from 7 to 5 while staying green.
- **§7.4's `--porcelain`-not-`git diff` argument is right and non-obvious.** On the landing commit every `dist/` path is untracked, so a `git diff HEAD` form is empty and passes vacuously. Naming the untracked-addition case as a required positive fixture (O-16) closes it.
- **§9's seven dispositions are all substantive**, not restatements. O-4's field-by-field closed-domain table (with the `writeFailures[].path` escape rule and `"<unprintable>"` fallback) and O-5's cause→`unlink`→rung table are exactly the kind of derivation that stops TSPEC building fixtures for unreachable states. O-15's "decided: no" with three reasons is a proper disposition of a decision obligation.
- **§13.1's structural NFR-2 discharge is genuinely checkable by reading** — manifest-driven managed set, one non-recursive listing, bounded spawns, no network — which is what NFR-2 asked for, and it correctly refuses to add a wall-clock assertion.
- **§0.3's honesty about undischarged prerequisites**, and §11.1's Option A/B table with its cost and risk columns, are the right way to hand an operator a decision.

## Recommendation

**Needs revision**

Must change before this FSPEC is implementable:

1. **F-01** — insert copy/backup/retire into §4.2's ordering and state, explicitly, which classification (pre-copy or post-copy) the drift state records on a sync run and how the post-copy state is obtained. Nothing downstream can be built until this is fixed; §5.7, §5.8, §4.3 and §6.2 all read from it.
2. **F-02** — §5.5 must back up `stale` rows before overwriting them, per AC-3.4, and an acceptance test must cover it.
3. **F-03** — reconcile §3.3's ladder with the declared row-reason precedence.
4. **F-04** — give §6.2 a terminal `blocked` row and a required-shape check.
5. **F-05** — record the AC-2.9(5) divergence as a REQ deviation (OQ-5's pattern) or conform to it and fix AT-18.
6. **F-06** — confront the LLM-mediated `_readFile` seam in §6.1: specify record validation, or state the residual.
7. **F-07 – F-10** — the four Mediums are each a one-paragraph fix but each falsifies a stated invariant.
