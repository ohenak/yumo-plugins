### 1a. The headline lesson: what actually broke the REQ loop

Three findings, in descending order of transferability.

**(i) The loop's convergence test rewarded leaving the layer.** Across all 16 rounds *not one* blocking finding contested user need, scope, priority, or phasing. Every one was an ambiguous acceptance criterion, a red/vacuous/unimplementable oracle, a cross-AC contradiction between clauses added in different rounds, or a measured platform fact contradicting a stated predicate — i.e. FSPEC, TSPEC, or PROPERTIES subject matter. The mechanism is simple and vicious: **a finding of the form "this AC has no oracle" is closable only by writing an oracle, and every oracle written into a REQ is new prose the next round reviews.** By v13 the requirements document contained a tab-separated trace-file grammar, a `PDLC_FAULT` fault-injection token vocabulary, an 85% branch-coverage floor, a jest fixture construction mandate with `realpath` normalisation, a `printf`-based JSON emitter with an escaping analysis, and a 96-cell property-generation axis table (of which 24 cells were undefined and unsatisfiable). Internal consistency across ~40 interlocking ACs became combinatorial and could not be preserved by hand across a revision — which is exactly when the blocking count stops falling.

**(ii) Fix-begets-finding was the *only* source of blocking findings in rounds 6–10.** The clearest chain, four consecutive rounds on one oracle: an assertion mandated to prove fixture provenance turned out to be red rather than vacuous (`git ls-files -s` on an untracked path prints nothing and exits 0) → the assertion was disclaimed as the ordering oracle, leaving the P0 ordering constraint with **no** observable at all → two test-only bash seams were added to supply one → the new seam's trace assertion was red against a correct implementation, vacuous on an empty trace, **and** its unknown-token rule made the SessionStart hook exit 4, contradicting a P0 "exits 0 for any reason" invariant in a different section. The same shape recurred in rounds 14–15 at much smaller scale (an AC-6.4 repair introduced a self-contradiction; an AC-6.6 replacement command introduced a false-green on untracked files) — which is why round 15's reviewer had to distinguish churn from plateau explicitly.

**(iii) The escalation path was a no-op, and that cost five rounds.** The first post-mortem's five recommendations (accept and narrow, carry findings to FSPEC, fix the harness, add a stopping rule, halt the queue) were all P0/P1 and **none was executed**. Three mechanisms failed at once: the queue status was never set to `halted`, so `orchestrate-queue` saw a `pending` row with `ready: true` and picked it up again; **no skill reads `POSTMORTEM-{phase}-{feature}.md` at phase entry**, so the recommendations were invisible to the run that followed; and the harness's own iteration bookkeeping was broken, so the loop could not tell how many rounds it had run. A post-mortem no agent consumes is not an escape hatch — it is one more artifact the loop writes on its way around again.

**What finally worked** is worth stating as the positive form: the loop converged only after a human, from outside the loop, (a) halted the queue, (b) restated the document at its own altitude and declared the specification-grade material downstream, and (c) **wrote the stopping rule into the document under review**, where every subsequent reviewer would read it. Both reviewers then cited O-13 by name in rounds 13–16 to justify routing Low findings downstream instead of triggering another revision. A stopping rule that lives only in a method document nobody loads does nothing; the same rule pasted into the artifact under review changed reviewer behaviour immediately.

### 1b. Loop-harness defect: wrong iteration index, 15 consecutive rounds, never fixed

The orchestrator dispatched every REQ round with a stale counter — round 16 was dispatched as "iteration 4" with instructions to read `-v3` and write `-v4`, while `v1..v15` sat committed on the branch and the document under review was v17.0. Both reviewers detected the skew **every single round** and refused; had any complied, committed review history would have been destroyed. First raised at round 3 (SE REQ v3 F-16) with the correct routing already attached; escalated by two post-mortem editions; **`git log` on the routed paths showed no commit through round 16.** Fifteen rounds of correct diagnosis and correct routing produced zero code change. The routing target was not being read by anything able to act on it. Now raised as its own queue row (8, `pdlc-review-loop-hardening`), which is the only mechanism in this repo that has ever caused a pipeline fix to happen.

A related, cheaper defect from the same family (SE REQ v3 F-01): a **version-bump-only edit was dispatched as a revision round**. The optimizer loop must not treat a metadata edit as a response to findings.

## 2. Cross-Feature Patterns

Two consecutive rounds with a non-decreasing blocking count is a fixed point, not slow convergence; a round in which the document grows while the blocking count does not fall is stronger evidence of the same. ## 4. Process Learnings

### 4a. Non-vacuity is the dominant defect class in this codebase — and the falsification discipline did not reach far enough

Every DoD round and both codebase rounds were, in substance, about the same thing: **green results that were green because the oracle was dead, not because the code was right.** The catalogue is worth keeping verbatim, because each entry is a distinct failure *mechanism*:

| Dead-oracle mechanism | Concrete instance | How it was found |
|---|---|---|
| **The comparator was described in the PLAN and never written.** The PLAN claimed a comparator that fails on any registered skip absent from the inventory. `grep` matched only the helper itself and three comments. Both exports were dead. | `REGISTERED_SKIPS` / `SKIP_INVENTORY` | DoD-02 |
| **…and even if written where the PLAN said, it would have been structurally vacuous.** Jest gives every test *file* its own module registry, so a module-level set can only ever hold that file's own skips — the subset check would be trivially true forever. Run-wide checks need `globalTeardown` or a reporter. | same | DoD-02 |
| **An oracle with no falsifying test at all.** The artifact-freshness gate that CLAUDE.md, PLAN §9, and the whole "rebuild `dist/` in the same commit" discipline rest on was only ever run on an already-fresh tree and asserted exit 0 — which passes whether or not the detector works. Neutralising **both** staleness assignments left all 997 tests green. | `build-runtime.mjs --check` | DoD-03 |
| **An exemption clause shadowed by an earlier clause, so never decisive.** Exemption (iii) had no detector: the only fixture manifest sat inside a tree already exempt under clause (i), so removing clause (iii) entirely kept every suite green. The assertion the PLAN cited was set-equality against a literal string array — helper output, not behaviour. | `isDistributionManifest` | DoD-04 |
| **A remediation resting on an untested *and* dormant transport.** The fix for a High finding was routed through a JSONL sink that no test touched (74% branch, uncovered region exactly the transport) and that fires on **no** non-root runner, so two of the comparator's three clauses evaluated over an empty record set every run — and `appendSkipRecord` swallows every error by design. If the sink broke, the run would stay green and the clauses would silently go vacuous: the exact class DoD-02 was raised about, reintroduced by DoD-02's own fix. | `skipSink.js` | DoD-11 (round 2) |
| **Correct-by-reasoning, green-by-accident.** `trap 'exit 0' ERR EXIT` was correct (under `set -u` a fatal unbound-variable error fires `EXIT`, not `ERR`), but reverting the `EXIT` arm left all 8 tests of the suite added to close that very finding green — because the new availability gate returns before any code that could hit a `set -u` fatal. | `check-workflow-drift.sh:43` | Codebase G-02 |
| **A probe list 16 deep with a fixture 1 deep.** The corrupt-library fixture defined only the *first* probed name, so the loop short-circuited and the other 15 entries were untested; and the gate's whole rationale ("this name is the library's last definition, so it witnesses a complete load") was pinned by a **comment**, not an assertion. Appending one function to the library silently demotes the witness. | availability gate | Codebase G-05 |
| **Documentation asserting a mechanism that does not exist.** A `.gitignore` anchoring rationale claimed an unanchored pattern would turn a fixture count from 7 to 0. False twice over: the checker walks the tree with `readdirSync` and never consults git, and ignore rules do not apply to already-tracked paths. Low **only because no test encoded the claim** — nothing was vacuous. | four sites | Codebase F-15 → G-04 |

The durable lesson is not "write more tests". It is this: **this feature had an excellent non-vacuity discipline that covered exactly the enumerated property set, and every dead oracle found in Phase CR and Phase DOD was outside that enumeration.** The `FALSIFICATION-LEDGER.md` rule (name the mutation in writing before running; red observed; revert verified; no nameable mutation ⇒ Residual, not green) was applied to all 63 `PROP-*` properties and worked — it even caught the `supersedingState` divergence as a Residual before a reviewer escalated it. But the freshness gate, the skip comparator, exemption clause (iii), and the release-checklist existence check were **ancillary oracles with no `PROP-*` id**, so nothing obliged anyone to falsify them, and all four were dead. Extend the ledger's domain from "properties" to "every assertion whose failure would be the only signal of a defect".

The second-order lesson: **verify remediations by mutation, not by reading the diff or the commit message.** DoD round 2 confirmed 7 of 10 fixes by mutation rather than by reading, and that is how DoD-11 was caught — a fix for a broken oracle that was itself a broken oracle. Phase CR round 2 did the same and found G-02 the same way. Reading the diff would have passed both.

### 4b. Test-suite coverage floors need a "why" column, not just a number

Three separate findings (DoD-13, and the round-3 informational notes) were about numbers below the stated 85% branch floor with no recorded explanation. Two distinct legitimate reasons appeared: subprocess execution (istanbul cannot attribute a child process), and fixture-construction error paths in test *helpers* that were never in scope. Both are fine; neither was written down, so each round re-litigated them. A floor plus a short list of recorded, evidenced exemptions costs two lines and saves a round.

### 4c. An out-of-band commit during a review window invalidates the review's own header

DoD round 3's two findings were **not caused by the feature**. A 206-line CI workflow was authored and committed outside the pipeline five minutes after the round-2 remediation commit and *while round 3's verification was running* — the tree was `?? .github/` at the start of the scan and a new HEAD by the end. Consequences, all real:

- **11 statements across 5 documents became false in the present tense.** REQ, TSPEC, FSPEC, PLAN and the operator-facing queue all asserted, as measured and binding, that hosted CI did not exist — and one of them used that absence as the *rationale* for an accepted residual, which the new job now re-detects on every PR. Every falsification cut in the safe direction (enforcement got stronger); what was wrong is that five specs described a repo that no longer existed.
- **A deferral was partially discharged while its successor row stayed `blocked` with a justification that was no longer true.** The row still existed, so the deferral-binding check passed; the row's *description* was what broke.
- **The next phase's gate changed under the feature's feet.** Before the commit, Phase PUB passed via the no-checks route after its 10-minute window. After it, the PR is gated on four never-executed jobs, two on a second OS, whose own commit message records "the Linux half of the matrix is unverified — the first PR run is its first measurement". A red matrix job is now easy to misread as a defect in this feature.
- **The review's own provenance header was invalidated.** Round 2's "working tree clean" and its measured branch tip no longer described what would ship.

**Rule:** a commit landed on a feature branch outside the pipeline during an open review window must be either (a) attributed to the feature and put through the phase it skipped, or (b) moved to the branch of the queue row that owns it. Whichever is chosen, record the decision — and never resolve the resulting doc falsification by deleting the out-of-band change to make the specs true again. The most valuable single remediation here was the **operator-facing queue note**, because unlike the spec documents it is long-lived and survives Phase H.

### 4d. Cost: where 205 commits and 22 batches went

This one REQ produced 66 process artifacts, 205 commits, 22 implementation batches, 66 PLAN task rows, 63 properties, and 1039 tests. The distribution of that cost is the actionable part:

- **REQ authoring and review consumed 32 of the 62 cross-reviews — over half the review budget for one document**, and about ten of those sixteen rounds produced no product-level change at all (the product content was uncontested from round 4 onward and unchanged from v13 to v14 except in altitude). This is the single largest recoverable cost in the feature, and §1a explains the mechanism. FSPEC (6), PLAN (3), PROPERTIES (3) and TSPEC (2) all converged normally.
- **The specification-grade material the REQ accreted was not wasted — it was misplaced.** REQ v13 remains in git history as the archived specification record, and its content became the FSPEC/TSPEC/PROPERTIES entry obligations in REQ §10. The cost was the *review* of that material at REQ altitude, sixteen times, by reviewers correctly holding it to a bar it could not meet there.
- **Phase 4 of the PLAN (the sourced bash library) was serial by construction** and occupied 5 of the 22 batches on its own; the landing step occupied 9 more (batches 14–22, strictly serial and order-sensitive, deliberately non-committing so any halt leaves an uncommitted tree with `HEAD` intact). Only about 8 batches were parallelisable. When a PLAN's critical path is a single sourced shell library plus an order-sensitive landing sequence, batch parallelism is not where the savings are.
- **Three DoD rounds, and only round 1 was about the feature.** Round 1 found 3 High / 3 Medium / 4 Low; round 2 found 0 High and one real Medium (itself a defect in round 1's remediation); round 3's two findings were caused entirely by the out-of-band commit of §4c. Two of three rounds were spent on remediation-of-remediation and on an external event.

### 4e. Reviewer discipline was not the problem — and the evidence of that is worth copying

It would be easy to read a 16-round loop as reviewer over-strictness. It was not, and the post-mortem re-tested that hypothesis against the evidence. Both reviewers, every round: delta-scoped to the actual `git diff` between revisions; opened with an explicit prior-finding disposition table; **verified every code claim by running a command against the tree at HEAD** rather than asserting it (measured POSIX traverse-vs-read permission semantics, index mode vs worktree execute bit, `git ls-files` exit codes on untracked paths, `git status --porcelain` vs `git diff HEAD` on untracked files, `--porcelain`'s silence on ignored paths); recorded positive observations; declined to relitigate settled points; and converged **independently** on the same small defect set each round (v12's SE and TE reviews name the same five defects in the same severity order). Author responsiveness was equally good: every High and Medium addressed in the following revision with a disposition table both reviewers verified as accurate. Two very strong reviewers plus a responsive author, all doing their jobs correctly, still produced a non-converging loop — which is precisely why the fix has to be structural (a stopping rule, a working escalation path, correct iteration bookkeeping) and not exhortative.

### 4f. Scope tagging was applied but thinly

Of 62 cross-reviews, only ~13 carried any `Cross-Feature` tag and ~18 any `Process` tag; the REQ rounds tagged almost everything `Local` even where the finding named a repo-wide mechanism or a sibling skill. The iteration-index defect is the clearest instance: it is a `Process` finding about `orchestrate-dev` that was tagged `Process` by SE but appears in TE's REQ files only as an untagged preamble note. Several findings routed here to §2 were re-scoped by this harvest under the under-tagging check. Tag under-use is itself the routing gap: an untagged repo-wide finding does not reach `consolidate-learnings`, which is one plausible reason fifteen rounds of correct routing produced no code change (§1b).

### 4g. A durable process artifact needs a stated lifecycle

`FALSIFICATION-LEDGER.md` was introduced as a tracked artifact with no disposition (PM PLAN v2 F-05): Phase H deletes only `CROSS-REVIEW-*` and `CODE_REVIEW-*`, and the guard hook watches only those two patterns, so the ledger would sit permanently beside this file with no way for a future reader to know whether it is live signal or spent scaffolding. Resolved by PLAN §3.1 declaring it **deliberately retained** as the standing falsification record. This harvest honours that: the ledger is read as input and **not** deleted. Any future artifact a PLAN adds to a feature directory should carry the same one-line disposition.
