| F-01 | High | Local | **The post-merge checkout strands the `done` row.** §8.2 orders the queue write-and-commit first, on `feat-{feature}`, then §8.3 checks out the default branch. But by then the PR is merged and (§6.4 default) the *remote* feature branch is deleted, so the `done` commit on the local feature branch has no route to the default branch — §8.2's "it rides the next PR" does not hold for a branch that is merged, closed and abandoned one step later. Worse, §7.5 makes the **driver's** post-pipeline `rewriteStatus(…, "done")` mandatory, and that write runs *after* the pipeline returns (`orchestrate-queue.js:818-826`), i.e. after §8.3's checkout — so it commits `QUEUE.md` on the **local default branch**, which is exactly the diverged-local-base hazard §8.2 rejects, arriving through §8.2's own fix. The FSPEC must state where the `done` row lands durably given the tree moves: e.g. §8.3's checkout is deferred until after the driver's transition, or the queue commit is pushed, or the row is re-applied on the default branch with the divergence consequence stated and accepted. As written the next queue pass reads `in-progress` from the merged base (the `in-progress` commit *is* in the PR, `orchestrate-queue.js:789-796`) and `selectNextPending` returns `blocked-active` — the permanent stall US-05 exists to prevent | §8.2, §8.3, §7.5 |

## Positive Observations

- Every code claim I could check is **true**. `Evidence` is safe against the header lookup: `colIndex` matches the substrings `order`/`#`, `status`, `feature`, `req path`/`req`/`path`, `depends`/`deps` (`orchestrate-queue.js:125-140`) and `evidence` contains none of them; unrecognised columns are ignored and round-trip. The separator predicate is `/^:?-{2,}:?$/.test(c) || c === ""` (`:144`), so an appended empty cell keeps it recognised, exactly as §7.3 says.
- §7.5's description of the driver is verbatim-accurate: `succeeded ? "awaiting-merge" : "halted"` and the "Merge the PR, then set it to `done`" message are at `orchestrate-queue.js:818-833`.
- §3.1's `O2` reuse is real and correctly scoped: `checkPrCi` returns exactly `passed|pending|failed|none|unknown` (`orchestrate-dev.js:3485-3525`) and the adapter already issues that identical `gh pr view --json statusCheckRollup` command (`runtime-adapter.js:838-850`). Reusing it rather than re-deriving is the right call.
- §9.3's "existing operator-facing notices channel" exists — `notices` is threaded through `buildFinalReport` on every report (`orchestrate-dev.js:5281-5318`), so `MERGE ESCALATION: ` lines need no new channel.
- §10.2's claim that no workflow script reads `.claude/pdlc.config.json` today is correct: the only reader is `pdlc_resolve_check_enabled` in `pdlc/hooks/scripts/lib/pdlc-drift.sh:840`, and the queue's drift gate consumes the drift-state record, not the config. The `merge` section is genuinely independent, and `readDriftStateSafely` (`orchestrate-queue.js:1354`) is a good precedent for a fail-closed script-side read of a `.claude/` JSON file through the injected read seam.
- §2.1's "Phase MERGE never throws" is exactly right and load-bearing: the phase body sits inside the `pipelineFn` try block whose catch writes a `halted` queue row (`orchestrate-dev.js:5117-5175`). Choosing `⚠️` rather than `❌` for deferred/refused also avoids `haltPhase` derivation picking up a non-halt row (`:5126`).
- The six observation points map cleanly onto the adapter's established fixed-command + exact-reply discipline (`rtGit`, `rtMakeCheckCi`), and §3.2's single fail-closed parse rule is the right shape for agent-transported output. NFR-1/NFR-4 are satisfiable as specified.

## Recommendation

**Needs revision** — three High and two Medium findings. F-02 and F-03 are internal control-flow
and data gaps that make the corresponding TSPEC rows unwritable; F-01 is a durability defect that
would leave the queue blocked on exactly the path the feature exists to unblock. All five are
narrow, local edits — none contests the design, the scope, or any REQ decision, and none needs new
sections. F-06 through F-10 are advisory and can be closed by a sentence each or routed to §13.
