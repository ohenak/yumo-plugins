| F-01 | High | Cross-Feature | **AT-C1 is pinned to the live repository and this feature's own run falsifies it.** Its Given is "this repository at HEAD — 5 LEARNINGS in corpus, 2 named in the legacy region" and its Then is "the un-consolidated set has **3** members; the volume test does **not** fire". Verified at HEAD: the corpus is exactly the 5 files §3.1 lists. But Phase H of *this* pipeline writes `docs/pdlc-consolidation-agent/LEARNINGS-pdlc-consolidation-agent.md` (REQ metadata table, row `LEARNINGS`), which the `docs/*/LEARNINGS-*.md` glob admits — so by the time this feature's own CI runs, the corpus is 6 and the un-consolidated set is 4, and AT-C1 is red on the PR that ships it. Two more delivered features make it 5, at which point `volume` fires and the `Then` inverts. An acceptance test must be stated over a **constructed corpus fixture** (n files, k named in the legacy region, threshold parameterised); the HEAD measurement belongs in prose, not in a test's Given. | §13.1 AT-C1, §2.3, §3.1 |
| F-02 | High | Local | **Step 8 is not implementable against the seam it reuses, so AT-M4 cannot be written.** §2.2 makes "Resolve the advisory model rung" a discrete step **8**, strictly after the consumed-pair append (7) and strictly before "Read the consumed LEARNINGS bodies" (9), and AT-M4's Given is "a pass that terminates `failed` at step 8". But `resolveAdvisoryRung` (`pdlc/workflows/orchestrate-dev.js:1833`) has signature `({ _agent, _log, _state, prompt })` and *dispatches* that prompt, falling back on a model-resolution error (`:1859`, `:1866`+) — resolution is observable only by performing a real dispatch. So step 8 is either (a) a probe dispatch of a throwaway prompt, or (b) fused with the first real dispatch in step 9 — in which case a `failed` pass **has** read bodies and O-C1's whole loss argument changes shape. The FSPEC names neither. A tester cannot construct the "terminates at step 8" fixture without knowing which. Name the step-8 dispatch (what prompt, what it costs) or restate the ordering claim in terms of the first advisory dispatch. | §2.2 step 8, §2.6, §13.3 AT-M4 |
| F-03 | High | Local | **The fallback-resolves branch — the one AC-1.6 exists to protect — has no acceptance test.** §2.6's table has three rows; row 3 (neither resolves) is AT-M4/S-11, row 1 is untested, and row 2 ("primary fails, fallback resolves; the pass surfaces `ADVISORY_MODEL_FALLBACK:` in its report; the fallback rung is named — never a silent downgrade") appears in **no** AT. §15.1 maps AC-1.5 to "AT-L5 (the `rung:` field)" and AC-1.6 to AT-M4; AT-L5 is a vocabulary set-equality check that asserts nothing about which rung ran, and AT-M4 is the halt path. | F-04 | High | Local | **§8.5's row-3/row-4 choice — the decision AC-5.3 explicitly delegated to this layer — is both untested and non-deterministic.** AT-F10 tests row 2 (a spent `revise`), AT-F11 tests row 1 (a spent `retire`); **rows 3 and 4, the ordinary choice, have no AT at all**. Worse, row 3's condition is "the recurrence names the same `symptom` the promotion targeted", and §8.1 defines `symptom` as "one line the pass's own model writes under no vocabulary", explicitly **non-keying**, precisely because two passes word it differently. A rule whose branch predicate is a free-text match by an LLM is not a rule two runs must agree on — it contradicts §8.3's "no model judgment, so two runs over the same inputs cannot disagree" and makes the `revision`/`retirement` field unfalsifiable. Either state the predicate over a decidable observable (e.g. whether the recurring LEARNINGS' `failure-mode-id` line carries the same id **and** the promotion's `artifact` still exists) or state that the choice is a model judgment and drop the determinism claim — then give rows 3 and 4 ATs. | §8.5, §8.1, §8.3 |
| F-05 | High | Cross-Feature | **AT-Q7 is an absence-only oracle evaluated by source inspection, with no positive conjunct on the same path.** "Given any code path of the pass, When the source is inspected, Then no merge or enable-auto-merge API call exists." Nothing asserts what the pass **does** do to the PR it opened. A grep-shaped oracle also cannot see a merge issued through a generic seam (`_gh(["pr","merge",…])`, a shell string, an API URL built at runtime), so it passes on the exact implementation shape most likely to regress. AC-3.7/§6.5 is the feature's central safety property and deserves a runtime oracle: a spy over the git/PR seam asserting the observed call verb-set is **set-equal** to the expected open-PR set, plus the positive assertion that the PR is in state `open` (not `merged`) after the pass returns. AT-M5's second conjunct ("that path appears in no pathspec of any pass") is the same defect in miniature. | §13.5 AT-Q7, §13.3 AT-M5, §6.5 |
| F-06 | High | Local | **AT-L5's oracle range is ill-defined, so the test is either vacuous or false on a correct implementation.** §10.3 asserts "Each field is a member of a vocabularies §1 category; **no field carries a value with no §1 row**", and AT-L5 asserts set-equality in both directions against §1 at `Version` 1.4. But of §10.3's 13 fields, §1 has rows for only three (`pr:`, `suppressed-by:`, `credential:`) plus the status/reason/trigger/route/verdict/state/action/phase categories. `rung:` carries a model id — at HEAD the ladder's literals are `"fable"` and `"opus"` (`orchestrate-dev.js:1652-1653`) — and `branch:`, `pass:`, `date:`, `consumed:`, `promotions:`, `deferred:` carry free values. All are "values the row emits" with no §1 row, so the "no value without a row" direction is **false** for any correct implementation, and a tester will save the test by narrowing its range to the enumerated fields — at which point the direction that catches a deleted row must be restated explicitly or it is lost. State AT-L5's domain exactly: which fields' values are in the compared set, and which are free-form and excluded. (The missing `rung:` row is an upstream defect — see the erratum below.) | §10.3, §13.9 AT-L5, §15.2 |
| F-07 | High | Local | **AT-C5 cannot fail, and its Given is self-contradictory.** "Given a log whose most recent datum-status row is a `refused` row followed by a `promoted` row … Then the datum is the `promoted` row's date; the `refused` row is skipped." A `refused` row is by definition *not* a datum-status row (§2.3 lists the four), so the Given contradicts itself; and under the natural reading (refused, then promoted) the `promoted` row is the most recent row **regardless of whether the implementation filters on status at all** — an implementation that takes the last row unconditionally passes. To falsify BR-03 the fixture must place the `refused` row **after** the `promoted` row, and the Then must assert the datum equals the earlier `promoted` row's date. | §13.1 AT-C5, §2.3, §18.1 BR-03 |
