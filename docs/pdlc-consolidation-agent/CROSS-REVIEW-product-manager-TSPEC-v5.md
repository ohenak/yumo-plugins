| F-17 | High | Local | **§7.3's new release decision silently deletes an enumerated FSPEC outcome: the empty marker.** The revision decides two things together (§7.3, `:865-889`): release is `await _writeFile(markerPath, "")`, leaving the file "**present and empty** on disk"; and `present` is `(await _checkFile(markerPath)).ok === true` and *only* that, so "**`file_empty` is treated exactly as absent**". Both halves of the argument check out against the code — I verified there is no removal verb in reach (`grep -n "unlink\|rmSync\|removeFile" pdlc/workflows/runtime-adapter.js` returns nothing; the adapter ships `rtWriteFile` at `:802`, `rtAppendFile` at `:863`, `rtListFiles` at `:905`, `rtGit` at `:945`), `rtCheckFile` is exactly at `runtime-adapter.js:817-831` and its command is `test -f … && test -s …`, so `{ok:true}` is *exists and non-empty* as claimed, and `fakeFs` doubles it (`__tests__/helpers/seams.js:292`). The reasoning about the `reclaim` arm is right too. **What is wrong is the consequence the section does not state.** FSPEC §4.2's take table enumerates four observed states, and its fourth row is `Marker present, unparseable **or empty (truncated write)** \| undecidable \| treated as **stale and reclaimed**, recording `reclaimed-stale-lock` with the abandoned pass id reported as `unknown` (DC-01 receive side)` (`FSPEC-…:442`). The FSPEC binds that row twice more: E-11 — "Marker file **truncated** or unparseable ⇒ **reclaimed, not refused**; the abandoned id is reported `unknown`" (`:2592`) — and its acceptance test AT-M3, whose Given is "a **truncated** or unparseable marker file" and whose Then is "it is reclaimed (not refused), with the abandoned id reported `unknown`" (`:2038`). A truncated write is precisely how a zero-byte marker arises, and it is the FSPEC's own gloss on "empty". Under §7.3 as now written, that state resolves `present=false ⇒ free`: the pass proceeds, and **no `reclaimed-stale-lock` is recorded**. The FSPEC's enumerated outcome is not narrowed or reinterpreted — it is unreachable. The document does not say so anywhere: §10.3 row 4 still reads "Marker **unparseable** ⇒ `reclaim`, `reclaimed-stale-lock`, abandoned id `unknown`" (`:1736`), having dropped the FSPEC row's "or empty" half without a word; §12.3 still assigns **AT-M3** to `consolidationPass.test.js` (`:2228`) as though the register row were satisfiable as written; and §7.3's own preceding paragraph still says `parseMarker` yields `null` for "**empty**, truncated, multi-line" (`:859-860`), which now reaches `markerVerdict` on the `free` arm rather than the `reclaim` one it was written for. This is the same class of absorption the document refuses everywhere else — §7.1 declines to mint an `unread:` log field because the field set is a vocabularies §3 contract, §13.3 routes the enumeration relaxation rather than settling it, T-08 says outright that AT-P7 "does **not** falsify the enumeration pair … rather than implying coverage it has not got" — applied to every question except this one. The collision may well be unavoidable (an empty file cannot distinguish *released* from *truncated*), and if it is, the right disposition is the one this document uses elsewhere: name the FSPEC row it cannot satisfy, state what it ships instead, and raise it upstream as an erratum against FSPEC §4.1/§4.2 so AT-M3 and E-11 are re-decided by their owner rather than left red. What it must not do is state `file_empty ≡ absent` as a settled local fact while three FSPEC artifacts say otherwise. Reconcile: (a) say explicitly that FSPEC §4.2's fourth row's *empty* arm is not satisfiable under this release form, (b) correct §10.3 row 4 and any §12 row that still claims AT-M3's truncated arm, and (c) raise the erratum. | AC-1.3 (`REQ-…:150-160`), FSPEC §4.2 (`:442`), E-11 (`:2592`), AT-M3 (`:2038`), BR-15 |
