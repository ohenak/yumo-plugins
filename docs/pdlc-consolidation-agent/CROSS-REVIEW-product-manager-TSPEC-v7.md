## Positive Observations

- **All three residual sweeps were taken, and two of them were taken further than asked.** F-20 asked for a spelling sweep and got a by-name withdrawal with the reason attached; F-21 asked for a type-to-runtime-value swap and got the swap plus the §11.3(b) chain that makes reading the module's own array a legitimate oracle rather than an echo. This is the same pattern I noted at v6 — the revision answers the finding's *purpose* rather than its literal text — and it is why the citation numbers hold up on re-check rather than drifting.
- **The new §12.2 empty-marker row closes a falsifiability gap I did not find, and states the gap before stating the fix.** The row's own argument is the strongest sentence in the round: until it existed, §7.3 decision 2 was "argued and not falsifiable", because every marker fixture §12 specifies (AT-M1 fresh, AT-M2 stale, AT-M3 unparseable-non-empty, AT-M4/AT-M6 absent, T-13 and the release row absent) gives the correct and the forbidden implementation the *same* verdict — the two diverge on exactly one input, a marker that exists and is empty, and no case constructed it. It then prices the miss in operator terms rather than test terms: §7.3's release form makes the zero-byte marker permanent, so that input "is the steady state of every consuming repo from its first pass onward", and the forbidden derivation would record `reclaimed-stale-lock` on **every** pass after the first. A decision recorded in five places at v6 was still unfalsifiable at v6; this row is what makes it a test rather than a paragraph.
- **The row is paired, not absence-only, and the pairing is the mechanism rather than a compliance note.** Conjunct (ii) — `reclaimed-stale-lock` absent — is asserted "**in the same case, paired against AT-M3's non-empty unparseable fixture, which *does* record it**", and §12.3 explains why it lives inside AT-M3's case rather than one of its own: "the pairing *is* the oracle: the two fixtures must be compared inside one case, and the non-empty half is already here". The fixture's feasibility is verified against the existing double rather than assumed — an own property whose value trims to `""` returns `{ok:false, reason:"file_empty"}` (`__tests__/helpers/seams.js:296-299` at HEAD, exactly as cited) and `_readFile` returns `""` for that same key (`:254-261`), "which is precisely what makes the pair discriminate, since the forbidden derivation reads that `""` as present-and-unparseable and sends both fixtures down the `reclaim` arm". No new helper, no new file, no new register id.
- **§7.3 withdraws its own call-order oracle rather than accumulating it.** The call-order prefix `["check", "read", "write", "read"]` is now "**authoring guidance only**, and deliberately so now that §12.2 carries the empty-marker discriminator", with the reason stated as a comparison of oracle strength: the behavioural row "fails on any implementation that reaches the wrong verdict however it ordered its calls", which the call-order assertion does not. Choosing the weaker-looking artefact to delete because the stronger one subsumes it — and telling a later editor explicitly that adding the call-order case "would add nothing this suite has not already got" — is how a spec stops growing test obligations it does not need.
- **The release row now says *which* `refused` it keys on, and the distinction it draws is real.** FSPEC §4.3's `refused` row reads "**no** — the marker belongs to the pass that holds it" for *Marker taken?* (`FSPEC-…:464`), which is true of the observed-fresh-marker refusal (§10.3 row 5 / AT-M1). But §10.3 row 5a's failed-take `refused` did write its `IN-PROGRESS` line before losing the read-back, so under this table's *test observable* — "`taken` iff the `IN-PROGRESS` line was written at some point" — its pair is `{taken: true, released: false}`. That is a divergence between the FSPEC's semantic column ("does this pass hold the marker": no, in both arms) and the proxy this table can observe, and the revision resolves it by scoping the table and assigning row 5a's pair to row 5a, with the failure mode named: "Keying on the status alone without that clause makes the row red on correct code for an implementer who reaches for the row-5a fixture". I re-read FSPEC `:458-465` to check this is a proxy artefact and not a contract divergence — it is: releasing nothing is correct in both arms, since "the loser never unlocks the winner" (`:464`), and the row says so. Finding a red-on-correct-code trap in a set-equality table before an implementer hits it is the class of defect these rows exist to prevent.
- **The PLAN hand-off records the new conjunct as task-neutral, which is the honest entry.** §13.3 item (vi) states that the conjunct "adds **no** file and **no** task — it is a conjunct inside a case that file's single owning task already writes — so the ownership manifest is unchanged", and gives the reason for recording it anyway: "so the task's Definition of Done names it and a PLAN reader does not read §10.3 row 4a as unowned". Batch-safety rule 2 stays satisfied without inventing a task to carry a sentence.
