| F-14 | High | Local | **AC-1.1 and AC-1.2 cannot both hold: the cadence-skip forbids the read the volume trigger requires.** AC-1.1: "given the interval has not elapsed, Then the tick exits `skipped-cadence` **without reading LEARNINGS**." AC-1.2: "Given the count of un-consolidated LEARNINGS … is at least `consolidation.volumeThreshold`, Then the pass runs on this tick **even if `consolidation.cadenceHours` has not elapsed** … The threshold is evaluated **by the pass itself**, not by the hook." Counting un-consolidated LEARNINGS *is* reading LEARNINGS (the AC-1.1 predicate is a basename scan of `docs/*/LEARNINGS-*.md` against the log, `pdlc/hooks/scripts/nudge-consolidation.sh:41`). So on a within-interval tick with 5+ pending files, one AC demands the pass run and the other demands it exit before it could ever know. A test writer must pick one, and the two fixtures are mutually exclusive: `(interval not elapsed, 5 pending)` expects `promoted` under AC-1.2 and `skipped-cadence` under AC-1.1. State the tick's actual order — enumerate the un-consolidated set first, then apply `cadence OR volume` — and restate AC-1.1's cheap-exit clause as something true (e.g. "reads no LEARNINGS *bodies*", which is a different and testable claim from reading none). | AC-1.1, AC-1.2 |
| F-15 | High | Local | **The cadence datum is defined circularly against a log that AC-7.2 now writes on every tick, so the cadence trigger provably never fires.** AC-1.1 measures the interval "since the last **logged pass**". AC-7.2 says "Given a pass completes **on any path**, Then exactly one report is emitted … written as the pass's **row in `docs/_decisions/.consolidation-log.md`**", and AC-7.1's closed terminal set includes `skipped-cadence`. Compose them: every `/loop` tick completes on some path, therefore every tick writes a log row, therefore "the last logged pass" is always the previous tick, therefore `cadenceHours` (default 168) never elapses. The volume trigger would be the only one that ever fires — and F-14 blocks that one. This is not a fixturing question: the document as written specifies a system whose primary trigger is unreachable, and the falsifying test is trivial (two ticks 10 minutes apart, assert the second is not `skipped-cadence` after 168 h of simulated time — it will be, forever). Fix by naming the datum precisely: the interval is measured from the last row whose status is in a stated subset (e.g. `promoted` / `no-op`), or `skipped-cadence` ticks write no row at all. Either is fine; the document must say which, because §4a's `cadenceHours` default is meaningless until it does. | AC-1.1, AC-7.1, AC-7.2 |
| F-16 | High | Local | **AC-5.2's `prevented` branch rests on an unobservable, so the determinism the AC claims — and NFR-4's well-definedness, which is stated to depend on it — holds for only one of three branches.** The rule is: `prevented` = no consumed LEARNINGS names the id **and** "at least one consumed LEARNINGS comes from a feature that **exercised the promotion's recorded `phase`**"; `insufficient-evidence` = "no consumed LEARNINGS exercised that phase". The revision deliberately grounds the `recurred` half — it adds a `failure-mode-id` line to the LEARNINGS §5 convention and even states the pre-convention fallback. It grounds nothing for the phase half. There is no phase field in a LEARNINGS file: per CLAUDE.md's artifact convention a LEARNINGS is a metadata table with a required `Harvested from` row, five numbered sections, and a best-effort `## 6. Approval Record` whose rows are `Document Type \| Round \| Role \| Verdict \| Approval Hash \| Reviewed Commit` — document types, not phases, and covering only the review-bearing phases (R/F/T/P/PT), never I, CR, DOD, H, PUB or MERGE. So for any promotion whose `phase` is Implementation or later there is **no** artifact from which "this feature exercised that phase" can be decided, and for the earlier ones only a proxy the REQ does not name. Two implementations will disagree on `prevented` vs `insufficient-evidence` for every input — which then desynchronises AC-5.3's counted-pass streak and AC-5.5's `unmeasurable` counter, both of which skip on `insufficient-evidence`. Name the observable (a field this feature adds to LEARNINGS, as it already does for `failure-mode-id`; or `Harvested from` filename classes; or the log's own record of which phases the pass's consumed features ran) or collapse the tri-state to the two branches that are decidable. | AC-5.2, AC-5.3, AC-5.5, NFR-4 |
| F-17 | High | Cross-Feature | **REQ-CONS-06's sole input does not exist in the shipping configuration, and AC-6.3 turns that emptiness into a proposal.** The rationale paragraph is right that `ESCALATIONS.md` is the one durable per-seam record, but it omits the precondition: escalations are written only by the advisory tier, which **ships disabled** — `advisory.enabled` defaults `false` and the tier is then provably inert (CLAUDE.md §Advisory tier), and this repo's `.claude/pdlc.config.json` carries `implementation` only, no `advisory` section at all. | F-18 | Medium | Local | **AC-1.3's marker-release set is not set-equal to AC-7.1's terminal-status set, and the two uncovered members are the two that matter.** AC-1.3 says the `IN-PROGRESS` line is "removed by the pass itself on every terminal outcome (success, `no-op`, or failure)". AC-7.1's closed set is `promoted` / `no-op` / `skipped-cadence` / `refused` / `failed`. Mapping: `promoted`→success, `no-op`→no-op, `failed`→failure — and `skipped-cadence` and `refused` are unmapped. Both readings are broken. If a `skipped-cadence` tick releases the marker, it releases a marker it never took (and, under F-14's ordering question, possibly one another pass owns).
